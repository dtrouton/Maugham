# Maugham/Views — area notes

The SwiftUI view layer for the project window. Composes the binder (left), editor (center), and detail pane (right) plus modals and sheets.

## Important files

- `ProjectWindow.swift` — the root view. ViewModifier-extracted modal stack (`CheckpointModifier`, `SessionAndNavigationModifier`, `CollectionPieceModifier`, `RewindModifier`, `PersonaModifier`) to dodge SwiftUI's body type-check ceiling. **When you hit "the compiler is unable to type-check this expression in reasonable time," extract a ViewModifier** — established pattern. `TopChromeModifier` (private to `ProjectWindow.swift`) owns the window's top chrome: the persona bar as a **window-toolbar item** (`.toolbar { ToolbarItem(placement: .navigation) }`, whole toolbar hidden in `⌘\` focus mode) plus the update/backup banners in a top safe-area inset. **Never put permanent chrome in a top `safeAreaInset` wrapped around the `NavigationSplitView`** — the inset is not propagated into the columns' own layout, so it occludes the top of both of them (it ate the binder's segmented picker and the right pane's segment row, 2026-07-25 smoke defect A). The banners survive there only because they are zero-height in the common case. The `NavigationSplitView` carries a `columnVisibility:` binding, written by `CanvasCollapseModifier` and by `PersonaModifier` and by nothing else — `⌘\` on the planning canvas collapses both side columns (spec §8A.3), and `.detailOnly` is the case that looks right and hides the canvas, because the canvas is the CONTENT column. The whole of the reasoning, including why the stash release lives in `PersonaModifier`'s synchronous handler rather than in a later pass, is in `Maugham/Canvas/AREA.md`.
- `PersonaMemory.swift` (in `Maugham/Models/`) — each persona's remembered binder + right-pane segment, persisted in `UIState` (schema v5). `PersonaModifier.applyPersonaChange` records the persona being LEFT and restores the one being entered; transient segments (`.find`/`.trash`) ride through and are never recorded. Do not add per-click recording — departure-time is sufficient and is why the reopen case is correct.
- `PersonaBar.swift` — the four-persona switcher (`PersonaBar` + private `PersonaBarButton`), mounted by `TopChromeModifier` as a window-toolbar item, so it carries no background/padding chrome of its own. Holds no mutation logic — clicking a segment posts `.maughamSetPersona` exactly as ⌘1–4 do, so `PersonaModifier` is the one code path a *writer-initiated* persona switch takes.
- **Persona is also written by two automatic routes, and neither goes through `.maughamSetPersona`** — reaching that handler would mean posting and then writing the binder on top of the segment it restores, a correctness argument resting on SwiftUI delivery order (tripwire 2). The two are `CanvasClaudeArrivalModifier.show` (Show on the Claude-arrival banner; deliberately does NOT record the departing position, because a look is not a choice) and `ManuscriptNavigation.go` (below; deliberately DOES, because ⌘1 has to bring the writer back to the tree they were arranging). Both call `PersonaModifier.applyPersonaChange` or state why they do not.
- `ManuscriptNavigation.swift` — **where a navigation to a manuscript document decides the persona.** Denver, 2026-08-02: *"if I'm moving to the manuscript I'm moving to Author — I shouldn't be writing the manuscript in plan."* `.maughamNavigateToDocument` (a `[[wiki-link]]`, the Inspector's Links row, the stats window), `.maughamNavigateToParagraph` (an annotation row, a history row, a task row) and `.maughamNavigateToScene` (a slugline, in the Scenes navigator or on Plan's Structure tab) all route through it. **Count the array in `ManuscriptForceCensusTests.test_everyNavigationReceiverStillRoutesThroughTheNavigation`, never a number in prose** — the scene notification was the one this list did not name for a whole slice, and it did nothing at all when clicked from Plan (slice 2 review, F2). It has **two** receivers on purpose: this one moves the window to where the script can be read, and `EditorCoordinator`'s scrolls to the slugline; the already-recorded first-click edge at `SceneNavigatorPane.subject(_:whenNavigatingTo:)` is therefore reachable from Plan too, and is deliberately not papered over with a delayed re-post. **The guard is `Persona.showsManuscriptDocuments` — the persona's own centre column — never `== .plan`**: Review and Publish centre the editor, and a reviewer ejected into Author cannot adjudicate. A `.project`-scoped navigate writes a background window's persona, and that is intended (the stats window is key; this window is the one that must move). **What was NOT a navigation**: leaving a transient segment. Emptying the trash used to move the binder home — it names no document, so nobody should be moved to Author — and closing find used to do the same. Neither exists: trash is a foot disclosure (Task 2) and find is an overlay (Task 1), so there is no segment left to be ejected from. A `Destination` carries no binder position at all since Task 7. **Closing find is not a movement**: find is an overlay of the whole left column (`ProjectWindow.treeFindActive`, `TreeFindOverlayTests`), so ⌘⌥F writes no segment and closing reveals the column that was underneath rather than returning anyone anywhere. `ProjectSearchView.close()` is its one exit — the ✕ and Escape both call it — and `ProjectWindow.applyCloseFind` is what it reaches.
- `ScreenplayScriptSource.swift` — **the second producer of `ProjectWindow.lastParsedScript`, and the reason Plan's Structure tab can list a screenplay's scenes at all.** The first producer is a mounted `EditorCoordinator`, which exists only inside `EditorHost`, which `existingEditorSwitch` mounts only when the centre column is a document — so in Plan the navigator got `nil` and drew "No scenes yet" over a script with ninety scenes (slice 2 review, F1). **A second PRODUCER, never a second value** (tripwire 6): `needsDerivation` is false the moment anything has produced a parse, so the editor always wins and the two cannot disagree. It derives from the **op log** — the live `Document.displayText` when the doc is open, `ProjectStore.derivedCache.displayText` when it is closed — and never from the `.fountain` (tripwire 20 / ADR 0018). Called from one `.task(id:)` on `binderColumn`, keyed on the predicate, so it is one parse per arrival and not one per body pass (tripwire 4). The single (segment × project type) pair that derives is asserted as a census in `ScreenplayScriptSourceTests`, not stated here.
- `BinderPaneToggle.swift` / `CollectionBinderPaneToggle.swift` — the left column's two shells, one per `ProjectWindow.BinderShell`. **Each is now the find overlay, one tree, the Exports footer and the trash's foot, in that order** — shell-finish stage 2b Task 7 deleted the segment picker and the six-arm switch under it. Which tree fans out through `TreePane(for:)` (`BinderView` / `SceneNavigatorPane` / `CollectionPiecesPane`), and the second toggle answering that its own way — `type == .screenplay` inline — is precisely how the 2026-07-02 bug shipped, which is why the derivation is a type rather than an arm. **Three questions these shells used to ask the SEGMENT were re-based onto the PERSONA in Task 6**, a task before the enum went: "is the centre the board" is `Persona.centresTheCanvas`; "does the manuscript status footer belong here" is `Persona.showsManuscriptDocuments`, narrowed by the subject (`ProjectWindow.showsStatusFooter`); the Exports footer is `persona != .plan`, which is the one gate that legitimately reads a persona NAME — all four personas have the same left column now, so nothing about the tree can tell them apart, and what is left is what the writer is doing. `ManuscriptForceCensusTests` is what keeps the Exports gate and every navigation receiver from being deleted without a wrong spelling left behind; the offender-spelling half of that census went with the enum, because a pattern nobody can trip is not a guard.

### The binder tree (shell-finish stage-2a, spec `2026-08-08-shell-finish-design.md` §3)

Every persona's tree — `BinderView` (novel/short-story), `CollectionPiecesPane` (collection), `SceneNavigatorPane` (screenplay) — carries the same furniture below its own rows: a **Research** section, a **Palette** section, and, per manuscript row, a **fold** onto that piece's own research. Selecting any row in any of it writes `BinderSubject`, the window's one subject (widened from `{.project, .item}` to add `.research(String)`, stage-2a Task 1). It was additive beside the `BinderSegment` strip (`.research`/`.palette` segments, `ResearchView`/`CollectionResearchPane`) for one slice; **stage 2b Task 7 deleted all of it**, so the tree is the only research surface and there is no second selection state to cross-write. `researchSubjectPlacement` in `ResearchSubjectColumns.swift` carried TWO guards through that transition and neither survived it — see that file's bullet below.

- `BinderTreeSections.swift` — **the Research and Palette sections at the foot of every tree.** One implementation mounted three times rather than one per host (three copies of the store wiring is the shape CLAUDE.md calls *a copy drifts*, and 2b deletes the two panes this replaces). **Mounting is two touchpoints and both are required**: the rows go inside the host's `List` (this view's own `body`, plus `BinderPieceFold` below for a piece's fold), and the presentations — the Add Link sheet, the error alert, the palette-card load, the deferred-rename commit — attach OUTSIDE it via `.binderTreeSections(store:state:selectedSubject:)`, because a sheet on a row inside a lazy `List` is presented from a view the list may unmount. A host with rows and no modifier draws a convincing tree in which every creation verb silently fails, and no row-count or selection test can see it — `TripwireGrepTests.test_everyBinderTreeMountsBothHalvesOfTheSections` censuses which halves each host file carries, with `test_binderTreeSectionsCensusFiresOnAHostMissingItsPresentations` as its planted-offender companion (both one-sided shapes, plus a file naming neither). **`BinderTreeSectionsState` owns the tree's disclosure state as of stage 3a Task 4** — `researchSectionExpanded`/`paletteSectionExpanded` (both default `true`, so a fresh window looks the same as it always did) and `expandedResearchGroups: Set<String>` (open ids only; a stale id sits harmlessly, same reasoning as `selection`). It lives on this `@Observable` reference type for `selection`'s own reason: the value has FOUR writers (the two `Section`s the writer clicks, `reveal(_:research:)`, and the window that calls it) spread across files, and a pile of `@Binding`s would re-thread every one of them. `reveal(_ itemId:structure:research:projectType:)` opens whatever it takes for that item's row to be on screen — the owning section **or the owning piece FOLD** (`expandedPieceFolds`, keyed on DOCUMENT ids, stage-3b Task 7), plus every ancestor group — and only ever OPENS; it never closes anything the writer had open, and it ANSWERS with the row the tree can now show (`.research(id)`, or `.item(ownerDocId)` where the row is inside a fold — a fold's rows are reached through the piece's row, which is where the chevron is; `nil` where no tree draws the id). **Its guard is OWNERSHIP, not existence**: it was `TreeWalk.contains` over the whole manifest, which every research id passes — so a collection piece's note, whose row is drawn in that piece's fold and filtered OUT of the shared section by `sharedResearchRoots`, opened the shared section onto nothing and left the fold shut. Ownership is asked of `TreeSectionDerivation` (`sharedResearchRoots`, `pieceFold`), the derivations the tree actually draws from, never of a second path-prefix spelling. A novel's LINKED note reveals through the SHARED section it lives in — the copy in a chapter's fold is a second drawing of the same row. `ProjectWindow.openResearchItem` and `handleShowLatestMCPNote` (Claude's Show) call it beside their existing subject write, closing the gap recorded since 2b: before Task 4 the tree's expansion state did not exist anywhere (`Section`s and `DisclosureGroup`s all took the no-binding initialisers), so a Show could point the window at a note without making the note's row visible. **Arrival is VISIBLE, not just true, as of stage-3b Task 8**: `reveal` only ever answered `true`/opens-a-flag — nothing scrolled, because no `ScrollViewReader` existed anywhere in the app before this task. `TreeScrollTarget: Hashable` (`.researchHeader`/`.paletteHeader`/`.row(BinderSubject)`) and `BinderTreeSectionsState.scrollRequest: TreeScrollTarget?` are the one-shot: ⌘⌥R/⌘⌥P set a header case beside their existing `…Expanded = true`; `openResearchItem`/`handleShowLatestMCPNote` set `.row(revealed)` from what `reveal` returned; the find-match handler (`ProjectWindow.findMatchScrollTarget`, `matchSubject`'s own twin) sets it on BOTH arms — a research match through `reveal` exactly like `openResearchItem`, a manuscript match straight to its own tag, since `reveal` only ever opens research furniture and a structure row is never behind anything closable. **Consumption is the shared `View.consumingTreeScrollRequests(_:state:)`** (extension beside `binderTreeSections`), called once by every host right after the `ScrollViewReader` that wraps its `List` — `TripwireGrepTests.test_everyBinderTreeHostConsumesTheScrollRequest` censuses the three call sites. **Two triggers, both required**: `.onChange(of: state.scrollRequest)` for a request written while this tree is mounted, and `.task` for its own mount signal — because the find overlay REPLACES the column (`BinderPaneToggle`'s `if treeFindActive`), so a request queued while it covers the tree (⌘⌥R, then Escape) has no mounted `List` until the tree remounts. `.id()` targets are unambiguous by construction: the two headers carry `.id(TreeScrollTarget.researchHeader/.paletteHeader)`; every structure/piece/script row carries `.id(BinderSubject.item(id))`, the same value its `.tag` already carries; the SHARED Research section's own rows (root and nested, via `ResearchTreeNode.appliesScrollIdentity`) and the flat Palette rows carry `.id(BinderSubject.research(id))` — but a piece FOLD's rows never do, because a novel's `.linked` fold draws the identical tag a second time in one `List` and `scrollTo` over two identical ids is ambiguous; `reveal` already resolves that by naming the SHARED row (or, for a piece-scoped note, the owning PIECE's row — a closed fold has no row of its own yet).
- `BinderTreeVerbs` (a value type inside `BinderTreeSections.swift`) — the ONE `ResearchTreeActions` bundle every row in every tree acts through, including a piece's fold. It is a value rather than a computed property on the `BinderTreeSections` view because `BinderPieceFold` needs the same bundle, and reaching into a view for it means constructing one — which is exactly the token the pairing census above reads as *a host mounting rows with no presentations* (a real design error the census caught during Task 6, since fixed by making the verbs a value). `create` selects what it makes and defers the rename until the manifest shows the new row (`pendingRenameId`, committed on `.onChange` by the presentations modifier); `perform` surfaces a store failure in the shared alert rather than swallowing it; `refuseDrop` always returns `false` and logs why. **The tree is multiselect as of 2b Task 3** — `selectionForRow` is `actingIds(forRow:)`, the tree's whole selection when the row is inside one and the row alone otherwise, so "Delete N Items", a multi "Move to ▸" and a batch drag all reach the plural store verbs the old panes used (`deleteResearchItems`, `moveResearchItems`) with no new store API. Only a HOMOGENEOUS research selection batches: a set holding the project row or a chapter degrades every research verb to the row it was aimed at, because the manuscript has no plural verbs to invent.
- `BinderPieceFold.swift` — **a piece row with research of its own unfolds to it**, inside a `DisclosureGroup` the host mounts around the unchanged `BinderRow`/`PieceRow` (still draggable, still renamable — the fold costs the row nothing it already does). One implementation for both `BinderView` and `CollectionPiecesPane`. It re-routes exactly two of `BinderTreeVerbs`' verbs with the document the fold hangs under: `newNote` (a `nil` parent id means the shared root everywhere else in the tree, but a note asked for from inside chapter three's fold has to land in chapter three, via `ResearchScope.document(id)`) and `internalDrop` (Task 7 — without the document, a drop landing in a fold would classify as an ordinary shared-research row and reorder shared research instead of joining the piece). **The fold's disclosure is the WINDOW's flag as of stage-3b Task 7** — both hosts' `DisclosureGroup`s take `treeState.foldExpansion(of:)` and the fold passes `expandedGroups: $state.expandedResearchGroups` into its `ResearchTreeNode`, so `reveal` can open a fold and the groups inside it; default is closed, exactly as the no-binding initialisers drew, and collapsing stays the writer's own click (`BinderPieceFoldTests.test_theWritersChevronRoundTripsThroughTheBoundState`). `TreeSectionDerivation.PieceFold.showsDisclosure` decides whether the chevron shows — `semantic != .none && !items.isEmpty`, asked as two separate questions on purpose, because a document that cannot fold at all and one that folds onto nothing yet are different manifest facts drawn as the same absent chevron. **`New Group` at a piece's root has no store API** (`ResearchScope.route` covers note/asset/link only) — unreachable today because `ResearchTreeNode` offers that verb on group rows only, but the gap opens the moment a `+` menu lands on a fold row; carried for 2b. **A `.linked` fold is a VIEW and offers no rename** (`ResearchTreeNode.offersRename`, final-review finding I2): a linked note is a shared item, so in a novel it is drawn twice in one `List` — in the fold and in the shared section — off one `renamingItemId`, and both rows mounted a `TextField` running tripwire 16's 30ms focus claim against each other. The row's rename binding is dead and its menu item absent in a linked fold; contained folds keep the verb because their rows are drawn once. The duplicate HIGHLIGHT stands and is intended — both rows are the one subject. For the same reason a drop that would REORDER a linked fold refuses (`TreeDropIntent.Reason.linkedFoldHasNoOrder`, finding I1): the fold draws `linkedResearchIds` and the only reorder the tree can perform is `moveResearchItem` over shared research, so accepting moved rows the writer was not looking at and left the fold unchanged. A `linkedResearchIds` reorder API is 2b's.
- `TreeSectionDerivation.swift` — **pure derivations, no store, no disk**, so the mount and this file's own tests can exercise them without a window: `sharedResearchRoots(research:projectType:)` (every top-level root except the palette group and, for a Collection, anything under a loose piece's `pieces/…/research/`) and `pieceFold(for:structure:research:projectType:)` (a document's fold, derived from `ProjectStore.researchRouting` and never restated: `.pieceFolder` → contained roots that expand, `.sharedPlusLink` → the document's `linkedResearchIds` resolved and drawn flat, `.sharedOnly` → no fold). The by-item overload exists because the by-id overload would walk the whole structure to find the very item a row was already handed — one walk becoming N on the window's body path (tripwire 4). `TreeSectionDerivationTests` covers every project type exhaustively, including that a Collection's piece-scoped roots never leak into the shared list.
- `TreeDropIntent.swift` / `BinderTreeDrops.swift` — **what a drag onto the tree means, and what the store is then asked to do about it** (Task 7, spec §3's "drag is scope"). `TreeDropIntent.classify(payloadId:target:structure:research:projectType:)` is the one pure decision function and it routes by **lookup, never by the shape of an id** — the payload is found in `research`, in `structure`, or in neither, and "neither" is a loud `.refuse(.unknownId)` rather than a no-op (the publishing-namespace lesson: fail loudly on a silent no-op). `TreeDropIntentTests.test_theGridCanTellALookupApartFromAGuessAtTheIdsShape` runs an id-shape guesser over the same probe grid and requires it to disagree with the real classifier on at least eight cases, so a future rewrite into a guess fails it; `test_theClassifierAnswersEveryTargetForEveryPayloadInEveryProjectType` is the exhaustive grid itself. `BinderTreeDrops.swift` (an extension on `BinderTreeVerbs`) performs what was decided — the classifier has no store and makes nothing happen on its own. Every drop closure in the tree returns `Bool` all the way down to `ResearchRow`/`BinderRow`/`PieceRow`'s own `.dropDestination` — a closure that returns `Void` and merely logs lets the row accept-and-discard invisibly, which is exactly what shipped twice (Task 4's two fix rounds; the second was caught only by the compiler's unused-result warning on a `.dropDestination` closure bound to its Void overload) before `TripwireGrepTests.test_theResearchRowNeverAcceptsADropOnItsOwnAuthority` and `test_everyDropDestinationInTheResearchSurfacesDeclaresItsBool` (with its own planted-offender companion, `test_theDropDestinationBoolCensusFiresOnTheShapeThatShipped`) pinned both directions. `test_everyDropTargetInTheTreeReachesTheClassifier` censuses that every mounted drop target actually calls `classify` rather than deciding on its own. **External drops (Finder files, browser bitmaps) still refuse everywhere** — a declared gap, not an oversight: the piece-root case has no store API (`importResearchFiles(toParentId:)` reads `nil` as the shared root), so filling it now would silently import to the wrong scope. 2b owns it, since 2b is also what deletes the panes where file-drop import lives today.
- **Two closed-set censuses guard what killing the strip could have silently reopened (stage 2b Task 8)**, both in `TripwireGrepTests.swift`. `test_noProductionSpellingOfTheDeadStripSurvives` (planted-offender companion `test_deadStripCensusFiresOnPlantedOffendersAndIgnoresComments`) greps production Swift for the five dead spellings — `BinderSegment`, `binderSegments(`, `binderHome(`, `findActive`, `selectedResearchId` — so a merge or a revert can't quietly bring one back uncaught. `test_theWindowsPersonaIsWrittenOnlyFromTheClosedSetOfDecisionSites` (planted-offender `test_personaDecisionCensusFiresOnAPlantedDirectWrite`) is T7's open question reframed: not every `selectedSubject` write moves the persona (`ManuscriptNavigation` does; a tree click does not), but the SET of sites that legitimately do is closed and named, never "the ones there happen to be today."
- `BinderTreeSelection` (inside `BinderTreeSections.swift`) — **the nil-refusing selection binding every tree's `List` uses instead of `List(selection: $selectedSubject)` directly.** An untagged row — the placeholder an empty section shows — is selected anyway by AppKit and writes `nil` through the binding (measured on `BinderView`'s old empty-state row, macOS 26.5), which would blank the centre column the moment a writer clicked "No research yet." `BinderTreeSelection.subject(_:whenListWrites:)` lets anything tagged (`.project`/`.item`/`.research`) through and leaves the subject exactly where it was on a `nil` write; `SceneNavigatorPane`'s own untagged-slugline projection calls this rule for the case it shares rather than re-deriving it. **The `List` selects a `Set<BinderSubject>` as of 2b Task 3, and the window's one subject is DERIVED from it** — `shown` projects the stored set through the subject on the way out (a subject the set does not hold, which is every programmatic write, collapses the tree onto it), `resolved` derives the subject on the way in: one row is the surface's own 2a rule unchanged, a grown set keeps its anchor, and an anchor that leaves is replaced by the first remaining row in TREE order (`ordered`, never `Set.first`). An empty write is the `nil` refusal generalized — neither the subject nor the selection moves. **There is no sweep for the set and that is deliberate**: `ordered` and `actingResearchIds` are both built by walking the live manifest, so a deleted id can come out of neither, and a second rule beside `SubjectValidationModifier`'s about what a dead id means is a rule that can disagree with it. `BinderTreeSectionsTests.test_clickingAnEmptySectionsPlaceholderLeavesTheSubjectAlone` and its planted offender `test_plantedOffender_aPlaceholderRowOnANaiveBindingClearsTheSubject` pin it.
- `ResearchSubjectColumns.swift` — where a `.research` subject actually renders (Task 5, spec §4 shipped early). `researchCentreRoute(id:in:)` resolves a research id to a palette card, a note, a preview, or nothing, through the same `research/palette/` path-prefix rule the old segment-based research arm used — one function, so the two arms could not drift apart while both existed, and **both columns call it**: the inspector's preview half mounted `ResearchPreview` for everything until the final review, so in Plan — where that column is the writer's only view of the item — a palette card previewed as the markdown of its source (`test_bothColumnsAskTheSameRoutingFunction`). Where the centre is the canvas (Plan), a `.research` subject never swaps the centre out — the board keeps its mounted identity — and previews beside it in the inspector column instead; where it isn't, the subject takes the centre outright (`PaletteCardEditor`/`ResearchNoteEditor`/preview per the route) — **editable, except in Review** (shell-finish stage 3b Task 6, Denver's ruling that Review adjudicates and does not edit from its own columns): `ResearchSubjectCentre.readOnly`, threaded from the mount off `Persona.editsResearchInTheCentre` (the ONE spelling, never `== .review`), swaps the `.paletteCard` arm to `PaletteCardReadHost`/`PaletteCardReadView` and passes `lockEditing: true` into `ResearchNoteEditor` — a locked editor (selectable/scrollable, no mutation), not an unmounted one. `PaletteWallCentre`'s card arm reads the same predicate for the wall's own card click. **A subject may only reach a column the writer can point somewhere else again from.** That guard was `leftPaneWritesTheSubject`, renamed `interimLeftPaneIsTheTree` in stage 2b Task 6 and deleted with the enum in Task 7 — it is the stage-2a final review's Critical, and it was a trap rather than a mis-route: the two of Plan's four tabs whose left pane was an old pane wrote no subject, so a research subject arriving from Plan's tree replaced the canvas inspector (region, scrap, line and item arms, and every Promote button) with no control anywhere in the window able to clear it — persisted through `UIState`, and Plan landed on one of those tabs, so a relaunch reopened into it. **Task 7 removed the STATE rather than keeping the guard**: every persona's left column is the tree. `ProjectSubjectReachabilityTests.test_everyWindowStateThatLetsAResearchSubjectStandCanAlsoClearIt` is the class of test that was missing and it still runs, now over the personas: wherever the placement is not `.nothingMoves`, some control in a visible column must be able to write the subject away. Its successor question — with the find overlay covering the column there is no row to click — is asserted beside it and answered *not a trap*: Escape puts the tree back, and `treeFindActive` is window `@State` that no relaunch restores. **And a placement is not a mount, which is stage 2b's final-review Critical**: `.besideTheCanvas` says the right column previews the item, but `DetailPaneToggle` renders `inspectorContent` from its `.inspector` arm alone and `Persona.plan.defaultPane` is `.inbox`, so every correct piece composed into a research row that put nothing anywhere. `ProjectWindow.revealResearchColumn` is the rule (guarded by the placement's own `previewsInTheRightColumn`, so no pane moves in the personas whose centre takes the item), `ResearchRevealModifier` observes an ARRIVING subject — `load()`'s restore is the one write from no subject at all and deliberately does not force the pane — and `openResearchItem`/`handleShowLatestMCPNote` call it explicitly, because pressing Open or Show on the item that is already the subject fires no `onChange`.
- `TreeTravel.swift` — **Denver's travel rule, 2026-08-12: a double-click on any tree row in a persona whose centre is the canvas takes the writer to Author, on that row's own subject.** Plan's centre column has nowhere to open a chapter, a research note or a palette card in place, so the double-click moves the window instead; elsewhere the tree already sits beside the document it names, so the same gesture does nothing (`TreeTravel.treeTravelDestination` guards on `Persona.centresTheCanvas`, never `== .plan` — the same discriminator `ManuscriptNavigation` uses, and for the same reason). The gesture (`View.treeTravelOnDoubleClick(_:)`) attaches to a row's **label leaf**, never its container — tripwire 9's exact scar, recorded in `TaskRow.swift`'s own doc comment: a whole-row `.simultaneousGesture` ate drag initiation across the row's interior. **The closed set of rows it reaches** — a structure row, each project type's own project row, a research/palette row, and the screenplay's script row (`SceneNavigatorPane.scriptRow`, added after the first pass missed it) — is `TreeTravelGestureAttachmentTests.expectations`, never a count here; a slugline is excluded on purpose, since it already navigates Plan→Author on a single click through `ManuscriptNavigation`. Posts `.maughamTreeTravel` with the row's own tag (never `state.selection`, which a double-click can race); `TreeTravelModifier`, mounted once on `ProjectWindow.body`, writes `selectedSubject` and moves the persona through `PersonaModifier.applyPersonaChange` — not through `ManuscriptNavigation` itself, which answers a different question (does the CURRENT persona already show a manuscript document) and would let Review's own never-eject-a-reviewer guard silently decide a case it was never asked about.
- `ResearchLinkPickerSheet.swift` — **"Link Research…" returns as a document row's context menu verb** (stage 3b Task 9), restoring what stage 2b's strip death and stage 3a's dead-code fix wave took out along with `LinkedResearchPane`, its only host — until this task the tree DRAG was the sole in-app route to `linkResearch`/`unlinkResearch`, a modality narrowing for a keyboard or VoiceOver writer. `BinderView.linkResearchVerb` offers it on a document row's context menu, gated on `ResearchScope.researchRouting(for:)` answering `.sharedPlusLink` — the same boundary the tree-drag path already enforces, so no verb shows on a group row, a Collection piece row, or a screenplay's script row (`ResearchLinkPickerTests`). **It mounts from `BinderTreeSectionsPresentations`, never from a row** — the row's whole job is to set `state.linkPickerDocumentId`, for the same lazy-`List`-unmount reason every other tree sheet mounts outside it. - `StatementPane.swift` / `StatementEditorHost.swift` — the Intent (⌘⌥N) and Visual Language (⌘⌥V) panes (M1A). The pane resolves WHICH statement through the pure `StatementPane.effectiveScope`; the host mounts `EditorSurface` (never `EditorHost`) with the sanctioned binding and nothing else. **Several things here are not obvious — count the numbered items, never this sentence.** (1) The text goes through `StatementTextTarget`, a plain reference box, because a statement's `Document` does not exist until the first keystroke mints it — absence is valid — and `makeCoordinator` captures its binding ONCE, so a binding closing over a `@State Document?` would write to the nil it saw at mount. The box also means the mint does not remount the editor mid-word. It is not a second text mirror (tripwire 6): the draft and the `Document` are mutually exclusive by construction. **The draft is KEYED BY SCOPE** (`typedBeforeItsFileExisted`, issue #21) and not a single value, because words with no file yet outlive the pane that was showing them: a single draft had to be emptied when the pane moved on, and `release()` emptied it mid-mint — one character typed into a chapter with no intent, one binder click, and the statement was created without it. Keyed, nothing needs emptying; `release()` no longer touches the words at all and `draft` simply reads the entry for the scope the pane is on now. The alternative that looks cheaper is worse than losing the character: with one draft the second undeclared scope's editor SHOWS the first's words and its mint writes them into the wrong statement (`StatementDraftHandoffTests`' planted-offender run, measured). (2) It is the first SECOND editor alive in a window that already has one — see `Maugham/Editor/AREA.md`'s "Two editors in one window", which is where the two things that broke are recorded. (3) **A `load` is refused on BOTH sides of `Document.load`, and the two refusals ask different questions.** After it, `loadMayBind` asks whether the pane still wants this scope — the superseded-load defect, where a load lands in the box the NEXT scope is using. Before it, and only once the statement's open gate is ours, `gateArrival` asks whether this statement is ALREADY in the box: the host has two openers (its uncancellable mint and its `reconcile`), and a writer who types into an undeclared scope, leaves and comes BACK gives both of them a true `loadMayBind` — same scope, no cancellation — so both bind and the first `Document` is dropped unclosed, two live `Document`s on one file. Waiting on the gate is a delay; the re-ask inside it is the fix, which is `ProjectStore.appendToStatement`'s own discipline. **Both refusals are about BINDING and neither is about the WORDS** (issue #21): every arrival deposits what was typed for its scope into that scope's own file, including the two that turn away — `loadMayBind`'s closes the `Document` it created *after* writing them into it, and `gateArrival`'s, which refuses before the load and so has no `Document` at all, opens one under the gate it already holds and closes it again, but only when there are words waiting.

  **Visual language takes pictures and intent does not** *(Task 12, spec §7)*, on one switch — `takesPictures` — with `StatementImageIngestTests.test_intentTakesNoPicturesAtAll` as the control that it is a switch rather than an oversight. **Paste and drop, and the reason they differ is `MaughamTextView.paste(_:)`'s synchronous contract.** `⌘V` inside the editor goes through the existing `imagePasteHandler` seam (`ResearchNoteEditor`'s) and inserts at the caret — but only when the statement already exists, because the well is derived from `Statement.path` and `vacantStatementPath` makes that path find-or-create's answer rather than a constant. With no statement the handler returns nil and finishes asynchronously on the other route, which is lossless and lands in the same place: an empty statement has nothing to be after. **The drop target is a well BESIDE the editor, never over it** — `EditorSurface` mounts a real `NSTextView`, which is the deeper AppKit view and therefore the one a drag is offered to first, so a SwiftUI `.onDrop` laid over it is a target whose delivery nobody can predict; `PaletteCardEditor`'s dashed strip is the shape. **A finished ingest names its destination and reads no view state to find one** *(review I1, rounds 1–2)*. `take` puts the ref in through `ProjectStore.appendToStatement`, keyed on the `Statement` the ingest itself returned. Two earlier shapes were wrong in the same way and are worth knowing: writing through `target` reached whatever the pane held *now*, and routing on `resolvedScope` did not help, because that marker describes the resolved SCOPE rather than whether the host is MOUNTED — and `⌘⌥N` is not a scope change here at all, since `DetailPaneToggle.segmentContent` gives the two kinds separate `case` arms and this host is **torn down**. The costs were an accepted drop with no text (a ref in a `draft` that a bind for another scope clears, or a `setFullText` on a husked `Document`) and a `visual-language_assets/` ref appended to the writer's *intent* prose. `leave()` now clears `resolvedScope` on the way out so the marker stops lying, but nothing about where WORDS go depends on it any more. **The gap this leaves is deliberate and the fix for it was measured and removed:** a picture landing in a scope with no statement leaves the editor showing its empty draft until the pane is next opened there. Binding the pane to close that gap made the writer's next keystroke `setFullText("a")` over a ref they could not see; unbound, that keystroke MERGES through the mint's `deposit`. A picture you cannot see yet beats a picture you lose. `pictureMessage` is cleared in `reconcile` for the same reason `resolvedScope` is: this host is deliberately not remounted on a scope change, so every `@State` here outlives one.

## Patterns

- **Right-pane mode-swap**, now scoped by persona ([ADR 0005](../../docs/adr/0005-right-pane-mode-swap.md), amended by [ADR 0025](../../docs/adr/0025-persona-shell.md)) — each persona offers a subset of `DetailSegment` via `Persona.panes`. Every pane has one `⌘⌥` letter, dispatched from the View menu in `MaughamApp.swift` rather than from `DetailPaneToggle`, so every one reveals a hidden inspector column (**count `DetailSegment.allCases` rather than a sentence here**; `DocSyncTests` holds the letters against `docs/guide/reference.md`). **A new right-pane surface is a `DetailSegment` case, one entry in `Persona.panes`, one arm in `DetailPaneToggle.segmentContent`, and one `Button` in that View menu** — and nothing in the picker or `ProjectWindow`. The content arm is not optional and not a bug: `segmentContent` is exhaustive with no `default`, so the compiler asks the question. `Persona.swift` claimed for two milestones that `DetailPaneToggle` was untouched; M1A corrected it there and here. **Not every `⌘⌥`-letter opens a `DetailSegment` any more, as of shell-finish stage 3a.** ⌘⌥O/⌘⌥R/⌘⌥P kept their letters but changed what they mean: `MaughamApp.swift`'s View menu posts `.maughamSelectProjectRow`/`.maughamRevealResearchSection`/`.maughamRevealPaletteSection` (`.keyWindow`-scoped, ADR 0021) instead of `postSegment(.outline)`/`(.research)`/`(.palette)` — the three `DetailSegment` cases those used to open are gone (Task 6). ⌘⌥O sets `selectedSubject = .project` (which is what puts `ProjectAltitudePane` on screen, above); ⌘⌥R/⌘⌥P set `state.researchSectionExpanded`/`paletteSectionExpanded` on the tree's `BinderTreeSectionsState` and are refused (no-op) while `treeFindActive` covers the tree, since the overlay is the tree's replacement rather than its sibling.
- **Notification-based modal triggers** — `.maughamOpenRewind`, `.maughamShowProjectSettings`, etc. Posted by buttons in subviews, observed by ProjectWindow's `MaughamEvent` receive helpers (see below). Keeps the modal-state ownership in the root view.
- **Scoped window events (ADR 0021).** `ProjectWindow`'s receivers use the `MaughamEvent` helpers exclusively — `.onKeyWindowCommand`, `.onProjectEvent`, `.onGlobalEvent` (grep-verifiable: no hand-written `isKeyWindow` guard survives in this file). Every post declares its scope at the post site; `ProjectWindow` never re-derives one. When adding a new event, pick the scope where you post (`.keyWindow` for menu commands the key window alone should act on, `.project(id:)` for data events windows on that project should see, `.allWindows` for genuine app-wide fan-out), then subscribe with the matching helper — don't hand-roll a filter in the receiver closure. Panes that need to know their own window's liveness (e.g. to gate a receiver) resolve it via `WindowAccessor`, not by caching an `NSWindow?` and treating `nil` as "closed" (`WindowAccessor` caches the window and never re-nils it on close — see `MaughamEvent.isLive`).
- **Dark-mode propagation to side panes** is a known carry-forward (lost twice). Re-check after touching theme code.
- **Empty-state top-anchoring** — Any pane that conditionally shows a `ContentUnavailableView` MUST give it `.frame(maxWidth: .infinity, maxHeight: .infinity)`, AND the enclosing `VStack` (when the pane has a top toolbar + content body shape) MUST get `.frame(maxWidth: .infinity, maxHeight: .infinity, alignment: .top)`. Without both, the empty state collapses to its intrinsic size and the parent vertically centers the entire pane — the toolbar floats to the window's middle. Bug recurs every time a new pane is added; the established panes (HistoryPane, AnnotationsPane, ProjectAltitudePane, TasksPane, CollectionPiecesPane) all have this treatment. (`LinkedResearchPane` carried it too, before it was deleted whole in shell-finish stage 3a Task 6.)
- **Inline rename TextField focus claim** — `BinderRow`, `PieceRow`, and `ResearchRow` use the same shape: `.focused($isRenameFieldFocused)` + a `claimFocus()` helper that `Task.sleep(30ms)` before setting focus to `true`. The 30ms deferral lets `List(selection:)`'s focus-claim pass settle first so the TextField wins the gesture race. Both `.onAppear` (for the "row appears in rename mode" path) AND `.onChange(of: renamingItemId)` (for the "context-menu Rename on a visible row" path) trigger the helper — idempotent, either alone is incomplete. **When adding any new rename-capable row, copy the BinderRow shape verbatim.**
- **Close-before-FS-surgery (tripwire 14) — now enforced by construction.** Moving or deleting a file the user might be editing MUST close the writing surface (so its autosave can't recreate the file at the old path) AND flush the research-note debounce, BEFORE the FS call. This discipline is no longer remembered per-site: it lives INSIDE the typed `DocumentStore` mover — `relocate(plan:)` / `relocateUserContent(affectedPaths:perform:)` / `trash(relativePath:using:…)` — which is the only legal way to relocate/trash a user-editable path. See **`Maugham/Stores/AREA.md` → "Typed user-content mover"** for the entry-point table, the boundary (which moves are intentionally left raw), and the `TripwireGrepTests` guard. **When adding a new mover of user content, route it through one of those three entry points — don't re-hand-roll the close+flush.**
