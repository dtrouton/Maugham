## 2. Findings (each triaged in §3; every Medium coordinator-verified against source)

### W1 [Medium] Post-relocate image-ref rewrite is not best-effort → a cosmetic write failure abandons the move after the FS move already committed (manifest↔disk divergence)
`moveResearchItems` Phase 3 relocates all files through the typed mover, then rewrites a moved note's `./<stem>_assets/` image refs so a dedup-renamed stem stays consistent. The read is best-effort (`if let content = try? String(contentsOf:)`) but the **write is fatal**: `try await documentStore.coordinatedWrite(text: rewritten, to: noteURL)` (`ProjectStore+ResearchMove.swift:242`). If that write throws, the whole function throws **after** `relocate` has physically moved the files, so **Phase 4 (manifest rewrite + `saveManifest`) never runs** — the in-memory/on-disk manifest keeps the OLD paths while the files sit at the NEW paths. Items appear missing and files are orphaned; the divergence becomes permanent on the next manifest save. The rewrite is purely cosmetic (fixing relative image refs after a `-2` dedup collision), so it must not be able to abandon the move. Reachable only when (a) a destination filename collision forces a stem rename *and* (b) the coordinated write fails — narrow, but the consequence is real data-visibility loss. — fix-shape: make the ref-rewrite best-effort (`try?` + log, mirroring `renameResearchPath`'s own copy) so Phase 4 always runs after a successful `relocate` — effort S.

### W2 [Medium] Moved note's `<stem>_assets/` destination is deduped only against the batch's `claimed` set, not the destination folder's real contents → collision throws mid-`relocate`
The note's `.md` leaf is deduped against `existingNames` (the real destination-directory contents) **plus** `claimed`, but its sibling `<newStem>_assets/` folder destination is only inserted into `claimed` — never run through `researchDedupedFilename(_, existing: existingNames + claimed)` (`ProjectStore+ResearchMove.swift:212-216`). `newStem` is derived from the `.md`'s deduped leaf, so if the destination already holds a `<stem>_assets/` directory **with no matching `<stem>.md`** (an orphaned assets dir — exactly what W1/W2 themselves can create, or a manual `.md` deletion), the `.md` leaf sees no collision and stays `<stem>.md`, but the `<stem>_assets/` step's destination already exists. `FileManager.moveItem` throws on an existing destination (the coordinator's `.forReplacing` option does *not* overwrite — confirmed), so the `RenamePlan` fails mid-`relocate` → partial move + stale manifest. — fix-shape: run `newAssetsLeaf` through `researchDedupedFilename` against `existingNames + claimed` and derive `newStem` from the deduped folder name (dedup the `.md`/`_assets` pair jointly) — effort M.

### W3 [Medium] Doc-drift ×3 (incl. mandated-read AREA.md): "cross-scope moves add/drop explicit links" — the store deliberately leaves `linkedResearchIds` untouched (containment-based association)
On 2026-07-17 (post-spec) the design switched: scope moves **never touch `linkedResearchIds`** — association is derived structurally from containment, so a manual link goes *dormant* while contained and *resurfaces* on move-out, while a containment-only association simply *severs* on move-out with no auto-link minted (`ProjectStore+ResearchMove.swift:270-276`; pinned by `ResearchMoveTests.test_moveIntoPiece_keepsDormantManualLink`, `test_moveOutOfPiece_containmentOnly_severs`, `test_manualLink_roundTrip_resurfaces`, `test_pieceToPiece_linksUntouched`). Three docs still describe the abandoned explicit-link mechanism: **`Maugham/MCP/AREA.md:34`** ("into a piece drops the now-redundant link; out of a piece adds one back so the association survives") — a **mandated read-before-editing** file whose header points the reader here for the tool's contract; `MoveResearchItemTool.swift:5-6` (header doc-comment); and `CollectionResearchPane.swift:449-450` ("Task 3 also cleans up any now-orphaned links"). Both halves are false: nothing is dropped (kept dormant) and nothing is added back (either it was never removed, or a containment-only association is not preserved). No live runtime bug — the tool's runtime `description` string is link-agnostic — but a future session reading AREA.md before touching link handling would code against the wrong model. — fix-shape: rewrite all three to describe containment-based (structural) association, not link bookkeeping — effort S.

### W4 [Low] `install()` overwrites a user-hand-edited `~/.claude/skills/maugham/SKILL.md` with no ownership marker or confirmation — CALIBRATED from Medium
`detect()` flags **any** byte-deviation from the bundled template as `.stale` (`ClaudeCodeSkillInstall.swift:29`), and the setup sheet's "Update" button then unconditionally overwrites via atomic `write` (`:36`) — so a user who hand-edited the router skill loses their edits on Update, and `install()` would equally clobber a same-path file authored by a different tool (no "managed by Maugham" sentinel/hash to distinguish stale-vs-user-edited). — fix-shape: add a sentinel/hash marker so a user-diverged file is not silently overwritten, or confirm before overwrite — effort M.
*Calibration:* the skills tracer rated this **Medium**. Verified real, but calibrated to **Low** — the file is an explicitly Maugham-managed router artifact (`install()` header: "the only mutation, only on explicit user action"), the UI surfaces `.stale` **before** the user chooses Update, and the whole contract of the skill is "overwrite to current so Claude Code fetches the live procedure." The loss is confined to a deliberate hand-edit of an app-managed config file behind an explicit click — a hardening gap, not accidental clobber.

### W5 [Low] Scratch-orphan variant of the accepted batch non-atomicity — a mid-`relocate` throw can strand files in `.maugham/scratch/<uuid>`
`relocate` Phase 1 moves slot-colliding items to `.maugham/scratch/<uuid>` before placing them (`DocumentStore.swift:525-530`); a throw after that point (e.g. W2's assets collision) leaves those files in scratch — at neither the old nor the new path — a nastier divergence than the "manifest lags at old path" the roadmap documents as the accepted non-atomic trade-off. — fix-shape: a scratch-orphan recovery/sweep on next load, or roll back completed scratch moves on throw — effort L. *Note:* fixing W1+W2 removes the two new triggers this milestone introduced; the residual is the pre-existing single-move exposure.

### W6 [Low] Selection `Set<String>` is never pruned after delete → single-preview path shows a ghost id
A stale (deleted) id left in `selection` drives `previewId(for:)` to a non-existent item → stale/empty preview (`ResearchView.swift:280-286`, `CollectionResearchPane.swift:435-441`). `orderedSelection` already filters stale ids for drags, so multi-select drag/delete stay safe; only the single-preview path is exposed. — fix-shape: prune `selection` (and `selectedResearchId`) against `manifest.research` after delete — effort S.

### W7 [Low] Hand-rolled tree walk duplicates `TreeWalk.collect(in:where:)`
`ResearchSelectionSync.orderedSelection`'s private `walk(_:)` (`ResearchTree.swift:119-131`) is a manual pre-order filter-by-id-membership, functionally identical to `TreeWalk.collect(in:where:).map(\.id)` — and the same file uses `TreeWalk.find`/`contains` elsewhere, so it's an inconsistency, not unawareness. Mac-only (doesn't touch the phone↔Mac contract). — fix-shape: `TreeWalk.collect(in: research, where: { selection.contains($0.id) }).map(\.id)` — effort S.

### W8 [Low] Unguarded `skill.files[0]` subscript in `skills/list`
`uri(for: skill, file: skill.files[0])` (`SkillsExtension.swift:51`) crashes the MCP request if a skill's `files` array is empty. Coordinator-verified as **unreachable in practice**: `files` is only empty if `contentsOfDirectory` (`SkillIndex.swift:117`) fails *after* `String(contentsOf: SKILL.md)` (`:107`) already succeeded for the same folder — which does not happen for static bundled resources. A defensive gap, not a realistic crash. — fix-shape: guard `skill.files.first`, skip/throw on empty — effort S.

### W9 [Low] CLI vs Desktop socket-env asymmetry in the setup sheet
The copyable `claude mcp add` command omits `MAUGHAM_MCP_SOCKET` for stable (relying on the binary's compiled-in `BuildVariant` default), while the Desktop JSON snippet always sets it (`HelpClaudeDesktopSheet.swift:64-71` vs `249-262`) — correct only because the `maugham-mcp` binary's compiled variant matches the app's. — fix-shape: set the socket identically in both, or document why they differ — effort S.

### W10 [Low] `cliCopied` never resets → "Copied" button stays permanently
`cliCopied` is set true on copy but never reset, unlike the Desktop `copied` which resets after 2s (`HelpClaudeDesktopSheet.swift:93-97` vs `291-299`). Cosmetic. — fix-shape: mirror the `Task.sleep` reset — effort S.

**Duplication watch (map-level, not scheduled):** the "`<stem>_assets/` travels with its note + ref-rewrite" knowledge lives in **both** `moveResearchItems` (`ResearchMove.swift:205-246`) and `renameResearchPath` (`Research.swift:704-723`) — the roadmap's "fixed at the shared plan-builder level" is only half true; rename keeps its own copy.
