It mentions "0.41" / "0.14.0" **zero times**. A reader concludes P3 is unshipped.
- **`docs/problem-map.md:58`** ("Let a trusted reader into the book on my terms") is still marked `~` with "A reader with a role of their own, checked per op kind, **is P3**" and "*(partial — labels only; **no … roles**)*" — but roles/permits are exactly what v0.41.0 shipped.

CLAUDE.md is correctly ahead (its Stores/OpLog/Views/Phone cells describe P3 plan-3 behaviour as built), so the two status docs disagree with CLAUDE.md and with the release notes. This is the F8-class recurrence the last audit already flagged (and the roadmap bullet *narrates its own prior instance* of this drift) — the structural cause is the 15 KB single-line roadmap bullet. — `docs/roadmap.md:273`, `docs/problem-map.md:58` — fix-shape: flip the roadmap bullet `•`→`✓` (or split any genuinely-unbuilt remainder — the per-span Apply, a durable trust-event log, the synced person key — into its own `•`), rewrite the P3a/P3c plan-status tails to "merged; shipped v0.41.0 + phone-v0.14.0 (2026-09-26), v0.41.1 (2026-09-27)", and reconcile `problem-map.md:58`'s `~`/prose with the shipped roles — effort: **S–M**.

### SW2 [Low] — `TrustVerdict` is stated as "six" in two prose spots; the enum has seven (carried F11, still open)
`Maugham/OpLog/AREA.md:24` says "`TrustVerdict`'s **six** answers" and `CLAUDE.md:115` (tripwire 39's parenthetical) lists six arms `(.mine, .admitted, .stranger, .revoked, .otherRoot, .noChain)` — both omit `.retired`, added in P2b. ### SW3 [Low] — The starter census verifies the `startedBy:` argument is *present*, not that its value is non-nil — **VERIFIED against source**
`TripwireGrepTests.structureItemConstructions`' matcher flags a construction only when `!args.contains("startedBy:")` (`MaughamTests/TripwireGrepTests.swift:10238-10240`). A future document-creating site that passes `startedBy: nil` (or a conditional resolving to nil for a `.document`) contains the substring and **passes the census**, while silently reverting that piece to today's rule — so its Mac no longer mints the opening first and a collaborator's words can land behind someone else's. The census's own docstring names this exact class (`TripwireGrepTests.swift:10157-10162`: "A construction that forgets the field does not fail: its piece silently falls back to today's rule"). This census was **added in this window** (P3c plan 2 Task 4). Today the single conditional site is correctly gated (`ProjectStore+Structure.swift:70`, `kind.itemType == .document ? thisMacAsAStarter : nil`), so this is a future-proofing gap, not a live bug. — `MaughamTests/TripwireGrepTests.swift:10238-10240` — fix-shape: add a planted-offender case passing `startedBy: nil` on a `.document` (documents the limit and proves the matcher's shape), or parse the argument value for document-typed constructions and require it non-nil — effort: **S**.

### SW4 [Low] — A non-root device merged under the root's label cannot be permit-narrowed (group-wide suppression)
`PersonGroup.offersPermitChange = records.allSatisfy(\.offersPermitChange)` (`Maugham/Views/PeopleAndDevicesModel.swift:528`), and a root record contributes `false` (`RegistryAdmission.changePermitOutcome:701`, `cannotChangeARoot`). So a writer whose Mac (root) and phone are merged under one label cannot narrow their own phone to a reviewer; the only path is Rename-to-split-first. Consistent with the "label = person" model and the label-wide `changePermit` verb, but it is a real capability change vs pre-grouping (the phone row used to offer a label-wide Change…). — `Maugham/Views/PeopleAndDevicesModel.swift:528` × `RegistryAdmission.swift:701` — fix-shape: **product question for Denver** — is the group-wide suppression intended? If a per-record narrow of a non-root record grouped with a root is wanted, allow it — effort: **M** (if a change is wanted).
