## 2. Synthesis over the three maps (the sweep payoff)

The four emergent-bug classes were checked at every hop of the claim→verify→recognise→silent-admit seam by all three agents. **One concrete cross-map collision survived to a finding (SW2); the rest were run to ground as actively-guaranteed-correct** (§5).

The surviving collision came from pairing the bug-hunt map's tension ("*a person's records under one label share the same current permit* is relied on at the recognition site but **not guarded there**") against the P3b permit-change map (`changePermit(everyRecordOf:)` documents a `PermitChangePartlyApplied` mid-batch write failure). Coordinator-verified against source: `changePermit(everyRecordOf:)` gates the whole act up front (`DocumentStore+Registry.swift:488-510`, "the whole act or none of it") but its **write loop** (`:513-524`) can throw after writing some records and before others, leaving two device records under one label with **divergent** permits. `recognise` then picks the **lowest-fingerprint standing record** as representative (`TrustRecognition.swift:231-242`) and `admitRecognised` installs *that* record's timeline (`RegistryAdmission.swift:639`) — so if the **un-narrowed** record sorts lowest, a *new* device of that person is silently admitted with the **stale-broader** permit. This is the "two correct features interacting" class exactly. It is **defended** (SW2's severity is Low): the partial-apply is a *surfaced* error (`PermitChangePartlyApplied: LocalizedError`, `DocumentStore+Registry.swift:1711`), so the divergence is never silent at creation; it requires an I/O fault mid-batch **and** the broader permit to sort lowest **and** a new-device-open race before the writer retries; and the blast radius is a **known, already-admitted person** getting a stale permit (author-instead-of-reviewer for Sam) — **never a stranger admitted**. No probe was dispatched; the suspicion was resolved by direct source reading.

### SW2 [Low] — Recognition's representative-selection × `changePermit`'s partial-apply can silently install a stale-broader permit on a new device — **VERIFIED against source** (the §2 synthesis finding)

## 5. Refuted / verified-clean suspicions (so the next sweep doesn't re-chase)

- **A new Critical/High/Medium correctness defect in the v0.42.0 person-key / recognition / silent-admission seam** — **REFUTED by all three agents independently**, and the security invariants are **code-guaranteed, not assumed**:
  - a copied claim cannot verify elsewhere — `RegistryReader.verifiedPersonClaim` rebuilds `signedContent(forDevice: RECORD.device)` from the **containing** record (`RegistryReader.swift:759-776`); the device is never taken from the claim;
  - domain separation — `SignedContent.kind = "maugham.personClaim.v1"` is inside the signed bytes (`RegistryPersonClaim.swift:56`), so a person-key signature over any other object can't read as a claim;
  - recognition reads **only this root's chain** — `thisRoot = author.fingerprint` (not `TrustTable.myRoot`), every holder set filtered by `chain.contains` (`TrustRecognition.swift:152-166, 234-242`); foreign self-signed roots are ignored, never a reason to ask;
  - `admitRecognised` installs the **current timeline permit** and declines `.unjudgeable` (`RegistryAdmission.swift:639-642`), carries the governing `unsignedSnapshot.mark` when it narrows, and passes `memory: nil` — it **never writes `AdmissionMemory`** (`:657`, by having no parameter to pass);
  - it runs **before** `admitRemembered`, which guards `labelNamesANarrowedPerson` **and** re-runs recognition (`RegistryPresence.swift:666-685`) so a narrowed person's new device never arrives with the whole book;
  - `.ask` (unknown) still raises the normal sheet (`RegistryAdmission.swift:637` → stranger path);
  - Debug/ad-hoc/test-host reach **no keychain** (test-host guaranteed in code via `PersonKeyStoreChoice.testHost` → create-refusing `InMemoryPersonKeyStore`; Debug/ad-hoc via the absent entitlement — see §4 merit-drop).
- **The publish `language` value as an output-read-back-as-input / path-traversal vector (#73)** — **REFUTED as live.** A written `language`/`metadata.language` is validated at the write + compile door (`validate(…, checksLanguageValues: true)`); `Republisher`'s `validateFrozenEdition` deliberately skips the language check, which is safe **because** language reaches a path *only* through `OutputFilenameBuilder.sanitizeForFilesystem` (strips `/`, NUL, leading dots, control chars) and nowhere else. **Known load-bearing assumption flagged for the future:** if a later change routes a language value into a directory or template path, this skip becomes a traversal vector — the safety rests on "language is never a path component except through the sanitiser."
- **`MCPError: LocalizedError` as a silently-unwired-after-refactor regression** — **REFUTED.** Adding the conformance (`MCPError.swift:155`) let `EditionStatus` drop its `(error as? MCPError)?.message` special-case cast; the bug-hunt agent found **no other** site doing the same cast, so nothing is left rendering the generic "operation couldn't be completed (error N)".
- **Mac vs phone claim-byte drift (cross-surface contract, tripwire 19/35)** — **REFUTED.** Both surfaces produce identical `PersonClaim.SignedContent{kind,device,personKey,personPub,name}` through the one Core rule `RegistryPresence.claimIntent`/`declareDevice`; the only per-surface code is the ~15-line store-construction shell (neither target can import the other's `TestHost`), and the decision itself is Core's `PersonKeyStoreChoice.choose`.
