## How to write the plan, which is the lesson c1 actually paid for

**Five of c1's plan premises were false, and every one was caught by measurement rather than argument.** Three would have shipped a defect; two would have written a rule into `AREA.md` whose stated *reason* was false — the worst failure mode available, because the next author tests the reason, finds it holds without the code, and deletes the code.

The specific ones, so you don't repeat them: `CGRect.intersects` is false only for a **null** rect, not an empty one; a "pixels changed" raster assertion cannot test draw order, because every part of a region is translucent; a value survives being read into a `let` and a live mode does not; a contract you lean on (`onClick` before `onDrag`) can also be the thing that breaks the obvious spelling; and reversing a *click* precedence without touching the *drag* creates the disagreement the reversal was meant to eliminate.

**So: do not assert platform behaviour in a plan.** State the requirement and the symptom, and let the implementer measure — that is what caught all five. Where you do state a fact, name the file and line you checked it against.

Two more, both from c1's reviews:

- **Cap the plan at ~10 tasks and expect the reviews to add to it.** c1 shipped 7 tasks and its last task accumulated *five* extra charges from earlier reviews. That is healthy; budget for it.
- **The whole-branch review earns its keep every time.** c1's found that `LineInspector` had no Delete button while `RegionInspector`, in the same pane and the same slice, did — invisible to seven per-task reviewers because each saw one inspector.

## Constraints that will otherwise be rediscovered

- **`ProjectWindow.body` has a zero expression budget.** A `@State` property is free; a body line is not.
- **`CanvasView.swift` has five source-layout contracts** in its header, enforced by tests that slice the file as *text*. Contract 1 *crashes* rather than fails; contract 5 fails if certain accessibility modifiers are named **in a comment**.
- Run `xcodebuild` in the **foreground**, one at a time — two invocations contend for one DerivedData. **Never dispatch two implementers at once**; they share the working tree.
- `-only-testing` takes `MaughamTests/<ClassName>`, **never a folder path** (runs zero tests, reports success).
- `./gen.sh` after adding any file; `project.yml` uses folder globs, so no manifest edit. **Never commit anything under `Maugham.xcodeproj/`.**
- SourceKit's `No such module` / `Cannot find type … in scope` is stale-index noise. The one real diagnostic is *"unable to type-check this expression in reasonable time"*.
- **Reviewer subagents on this harness go idle without reporting.** Send them a message asking for the verdict; they answer in full. Budget one extra round-trip per review.
