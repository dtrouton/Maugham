## 2. The synthesis payoff: the prior High is closed; the proposed new High is by-design

The two op-log agents (tracer + delta bug-hunt) between them settled the two questions this window most needed answered:

### F1 (2026-09-20's sole High) → **CLOSED — VERIFIED against source**

The prior audit found that `OpLogChain.verify` consulted the `trust` closure **only** in `case .seal`, so a signed foreign device's **unsealed tail** (up to 99 ops, or its whole pre-first-seal file) merged into the manuscript un-gated. That finding was scheduled into P3 as **Task 11** (`docs/superpowers/notes/2026-09-17-signed-op-log-p3-handoff.md:175`, "an unsealed span answers to its file's verdict"). The fix is now real, complete, and correct across every op-read path:

- **Chain layer** — `verify` runs `judgingWhatNoSealHasClosed` after the walk (`Packages/MaughamCore/Sources/MaughamCore/OpLogChain.swift:956`), judging every still-`.unsealed` line by the file's own key in three arms (arm 1 = last verified seal key; arm 2 = `keyOfAnUnsealedFile()` filename-slug → register; arm 3 = leave applied — the unsigned door). `settlingAnUnsealedSpan` (`OpLogChain.swift:1211`): `.stranger` → `.pending` (held), `.revoked`/`.otherRoot` → `.quarantined` (refused), `.mine`/`.admitted`/`.retired`/`.noChain` → nil (applied). Both `.pending` and `.quarantined` are `isHeldBack` (`OpLogChain.swift:456`).
- **Store layer** — every production `verify` call now threads `keyOfAnUnsealedFile: { PermitMark.keyNaming(url, in: table) }`: `classifyTail` (`OpLogStore.swift:2224`), the segment fallback (`:2499`), `loadSyncMerged` (`:1773`), `TranslationStore` (`:284`), `JSONLAppendStore.chainedAppend` (`:131`).
- **Enforcement** — every op-read path parses `applied(...)` which emits only `!isHeldBack` lines (`JSONLAppendStore.swift:242`; `OpLogStore.swift:2255,:2442,:2508`), so held/refused lines never become `Op`s and the derived `.md` never receives them. No Mac/phone drift — the gate is in shared MaughamCore, which the phone's `AnnotationLoading.loadJudged` also runs. `test_anUnattributableVerdictCanOnlyHoldOrLeaveASpanAlone` pins that arm 2 can only make a span *stricter*, never gentler.

### The delta bug-hunt's proposed High → **REFUTED as a defect (documented, deliberate)**

The delta hunter proposed [High] that `handleExternalDiskChange` (`Maugham/OpLog/Document+ExternalChange.swift:43-53`) rewrites (blanks) the derived `.md` for a **holding** document without the C12 `rendersOnItsOwnAccount` guard that its two siblings (`handleExternalLogChange:297`, the diverged-load path `Document+Load.swift:714`) received — the "silently-unwired-after-refactor / two-correct-features-interacting" shape. **The mechanism is real, but the classification is wrong**, established on source-verification (invariant 3):

- The behavior is **explicitly documented as intended** in `Maugham/OpLog/AREA.md:36`: "`handleExternalDiskChange` still rewrites an open document's `.md` whenever another Mac's differs, **held lines or not**, until F7's damping — the held-lines rule adds no trigger, and removes none of that one's." That prose was written in the same P3-plan-3 pass that added the C12 guard; the C12 commit (`8b050cb`) touched only the re-read and diverged-load paths and its own diff comments reference `handleExternalDiskChange` — the author considered it and left it rewriting-until-damped.
- The **hard-invariant rationale is coherent**: `handleExternalDiskChange` fires on *any* `.md` file change and cannot distinguish a genuine external edit (TextEdit) from another Mac's synced render — both arrive as `diskMd != ourClean`. Applying the C12 guard (skip the rewrite while holding) would let a genuine external `.md` edit to a holding document **survive on disk**, violating the "external `.md` edits are never honored" hard invariant. AREA.md states this trade explicitly ("Skipping the rewrite for a repeat is NOT the fix: the same outside edit, re-applied, would then survive on disk"). The design chose **F7 ping-pong damping** (`_discardCount ≥ discardDampThreshold`, `Document+ExternalChange.swift:43-51`) as the disk-path mitigation instead of the C12 guard.
- **Non-lossy and bounded**: the words persist in the op log (on the applying Mac) and in this Mac's `.maugham/conflicts/` backups; F7 damping (now counting every discard, commit `d185c45`) bounds the ping-pong to `discardDampThreshold-1` rewrites, after which the last-delivered (fuller) `.md` is left on disk; and the admission / *Theirs* decision re-reads and renders full (as does any keystroke).

Recorded in §6 so the next audit does not re-chase it. It is nonetheless a genuine **seam tension worth Denver's awareness** (§5): the C12 guard and the F7 damper are two just-shipped fixes protecting the *same* cross-Mac-divergence harm by different means in different callbacks, and their guards don't compose — a holding Mac's human-readable `.md` is transiently blanked before damping engages.

## 5. Watch-notes (future-fragility / temporal coupling — not defects today)

Recorded for the next audit's synthesis; each is correct now and correct-only-because-something-else-holds.

- **Option A cooperative-vs-enforced is a two-correct-features shape.** The write side (`OpLogStore.localWritePermit`'s `mine`, `OpLogStore.swift:360-366`) and the read side (`PermitPartition.appliesOnItsWritersOwnMac`, `PermitPartition.swift:911`) compute the *same three Option-A facts* ("her device started it / not taken / nobody wrote its text") in **two places by design**. They cannot disagree at load time today, kept in step only by shared `TrustTable`/`Permit` predicates and the `restampWhereItsStarterArmMayHaveClosed` re-stamp (ruling H). A change to one starter predicate that misses the other would drift **silently** — the classic "the Mac lets her type what its next read sets aside." This is a temporal-coupling pair (`localWritePermit`/`localWritePermit`-adjacent files co-changed with `PermitPartition` 10× in the window) worth an explicit test that the two computations agree on a matrix of starter states, if one does not already exist.
- **The C12 guard and the F7 damper don't compose on the disk path** (§2, the refuted High). Two fixes for the same cross-Mac-divergence harm landed in different callbacks; a holding Mac's human-readable `.md` is transiently blanked (up to `discardDampThreshold-1` rewrites) before damping. By-design, but the seam is fragile: a future change to either guard should re-check the three render paths (`handleExternalLogChange`, the diverged-load path, `handleExternalDiskChange`) together.
- **`performAutosave` is the common render choke point and has no posture/holding guard** (`Document.swift:826`) — only closed/recovery/`rendersToDisk`. Correct (rendering is not a signed text write), but it pushes the "should I render now while holding?" decision out to each *schedule* site, and the disk-change site is the one that (deliberately) answers differently. If a fourth render-schedule site is ever added, it must make that decision explicitly.
- **A book author's Mac yields (locks, with Edit Anyway) to a starter the register cannot even NAME** — for a piece started by a device whose record hasn't synced, the surface reads "Somebody else started this piece", which is odd UX for a piece the writer may have started on their own not-yet-synced Mac. Safe (don't let a keystroke claim), documented; noted as a UX rough edge, not a defect.
