## 2. Findings (each triaged in §3; every High coordinator-verified against source)

### S1 [Medium] "Role identity survives rename" has a legacy-project hole — rename before first heal loses the group/craft-intent identity permanently — CONFIRMED probe
`PaletteLookup.paletteGroup` falls back to an **exact** `path == "research/palette"` match, and `craftIntentItem` to `lastPathComponent == "craft-intent.md"` (`PaletteConvention.swift:17-20,:30-31`). `role` is stamped only by `ensurePaletteGroup`/`stampRole` (`ProjectStore+Palette.swift:36,45,205`) or the lazy `healRole` inside `paletteGroup()`/`paletteCardItems()` (`:18,:197`). But the binder header renders the **pure, no-heal** `paletteGroupDisplayTitle` (`PaletteWallView.swift:20`, `PaletteBinderList.swift:15`), and a group/doc is renamed from the **research binder**, which never calls `paletteGroup()`. So on a **legacy project (role==nil)**: rename the palette group away from `research/palette` (or the craft-intent doc away from `craft-intent.md`) before ever opening the palette wall since upgrading → role check fails AND the exact-path/filename fallback fails → `paletteGroup()` returns `nil`. Not self-correcting: a subsequent `ensurePaletteGroup()` sees no existing group and **mints a fresh empty `research/palette` group**, orphaning the renamed group's cards into ordinary research. Contradicts the milestone's headline claim for the legacy path (roadmap: "role-first lookups … survive rename"). Cards are recoverable (rename back), but the feature silently stops recognizing them. — fix-shape: eager one-shot role heal at project load for the known legacy path/filename (stamp on load, not lazy-on-lookup), so the window closes before any rename is reachable — effort S–M.

### S2 [Medium] The shared role-lookup substrate is cross-surface Tier-1 but has no registry row; `PaletteCard` row prose is now false
`PaletteLookup`/`ResearchRole`/`PaletteConvention` are consumed by **phone production** (`PaletteAimPicker.swift:51`, `PaletteLoading.swift:15,28,33`, `BinderView.swift:28`) and Mac (`ProjectStore+Palette.swift`, `+CraftIntent.swift`) — a genuine Tier-1 shared impl — but there is **no row** in `docs/superpowers/notes/cross-surface-contracts.md` (verified: only row 45 `PaletteCard` and row 46 inbox-fields cover this milestone). Separately, row 45's prose still says PaletteCard has "**no phone consumer yet (palette is Mac-only today)**" — false as of this window; the phone Read tab now parses it (`MaughamPhone/Read/PaletteCardView.swift`, `PaletteLoading.swift`). The registry exists specifically to catch the phone-v0.1.1 drift class; a shared type with no row + a row that misdescribes the surface footprint is the drift-surface itself. — fix-shape: add a Tier-1 registry row (choke-point `PaletteLookup`/`PaletteConvention`, tests `ResearchRoleTests`+`PaletteAimTests`+`PaletteLoadingTests`) and correct row 45's "no phone consumer" prose — effort S.
*Calibration:* the doc agent rated the missing row **High**. Verified real, but calibrated to **Medium** — it is a registry-coverage gap plus stale prose in a *drift-surface notes file*, matching the 2026-07-11 audit's **E5** (Medium) precedent for "registry doesn't cover X", not an active false claim in a mandated first-read file (which the prior audit rated High/Critical). No live behavior is wrong today; the substrate is single-impl.

### S3 [Medium] Phone re-types the sense vocabulary as a bare literal — tripwire-19 drift vector (double-confirmed: bug-hunt + tracer)
`PaletteAimPicker.swift:36` hardcodes `["sight","sound","smell","touch","taste"]` while the Mac editor (`PaletteCardEditor.swift`), the Mac pane, **and the phone's own reader** (`PaletteLoading.groupedNotes`) all derive from `PaletteCard.Sense.allCases`. The `InboxEntry.swift:97` comment justifies it as forward-compat ("older Core needn't know the sense list"), but the phone already couples to `PaletteCard.Sense` elsewhere, so the rationale is thin here. A 6th sense added to Core is silently un-offerable from phone aim; a rename desyncs the writer's string from the Mac's tolerant `Sense(rawValue:)` map. — fix-shape: `PaletteCard.Sense.allCases.map(\.rawValue)`, or a parity test pinning the literal == `allCases` — effort S.

### S4 [Medium] `MaughamPhone/AREA.md` overclaims `groupedNotes` is "parity-tested"
`AREA.md:89` says the Mac (`PalettePane.groupedNotes`) and phone (`PaletteLoading.groupedNotes`) grouping is "mirrored + parity-tested," but no test compares the two against shared input — each has an independently hand-typed expectation (`PalettePaneTests.swift:14-23` vs `PaletteLoadingTests.swift:110-124`). "Independently tested" is accurate; "parity-tested" overclaims. — fix-shape: a real cross-target parity test (one fixture asserted against both), or reword the claim — effort S.

### S5 [Low] Empty text→palette promote silently vanishes on the next parse — emergent two-feature interaction (double-confirmed)
The `.text` promote branch lacks the empty-content guard the `.audio` branch has (`InboxStore.swift:251-254` vs `:256-257`), so an empty/whitespace-only capture appends an empty **untagged** `SensoryNote`. The renderer emits that as `"- "` (`PaletteCard.swift:262`); the parser requires `hasPrefix("- ")` after trailing-whitespace normalization, so `"- "` → `"-"` fails to match (`:165`) and the note is **dropped on the next reparse** — lost on the following edit. Tagged-empty notes survive; only untagged-empty is lost. Reachable only through the missing text guard. — fix-shape: guard the text branch like audio, **and** have the renderer skip fully-empty untagged notes (or the parser accept a bare `-`) — effort S.

### S6 [Low] `addPaletteCard` raw uncoordinated write — new facet of the scheduled A1
`ProjectStore+Palette.swift:56-57` writes the card template via raw `.write(to:atomically:)`, the same NSFilePresenter-uncoordinated write as `updatePaletteCard` — but the scheduled A1 names only `update`. Card **creation** (incl. the InboxPane "New Card …" promote) has the identical exposure. — fix-shape: fold `addPaletteCard` into A1's coordinated-write fix (same call-site treatment) — effort S.

### S7 [Low] `ResearchRole.unknown` re-encodes as the literal `"unknown"`, clobbering a genuinely-newer durable role
`ResearchItem.swift` decodes an unrecognized role as `?? .unknown`; the synthesized encode writes `.unknown`'s rawValue `"unknown"` back out. Unlike a `nil` role (omitted via `encodeIfPresent`), a **future** role value decoded on an older build is overwritten with `"unknown"` on any manifest save (including a lazy heal), degrading a forward build's identity marker. Narrow (cross-version downgrade; paired release + self-healing mitigate) but `role` is identity-bearing, so it deviates from the safe ADR-0015 round-trip more consequentially than the `ItemType`/`AssetKind` `.unknown` cases. — fix-shape: `case unknown(String)` preserving the raw value, or omit `.unknown` on encode — effort M.

### S8 [Low] Non-atomic palette promote can silently double-append a note on retry
`InboxStore.swift:275` flips the entry to `.promoted` via a non-throwing `updateStatus`. If `updatePaletteCard` succeeds but the status append fails, the entry stays `.new` while the note is already on the card; a retry double-appends. For `promoteToResearch` a retry yields a *visible* duplicate item; for palette it's a **silent** extra bullet inside an existing card. — fix-shape: surface the status-flip failure, or dedupe notes on append — effort M.

### S9 [Low] `read_inbox_entry` serializes dates as raw reference-date Doubles (off-seam inconsistency)
`InboxTools.swift:86` encodes the entry with a bare `JSONEncoder()` (default date strategy), so `created_at`/`written_at`/`resolved_at` go to Claude as numbers, inconsistent with `list_inbox`'s ISO8601 (`:57-58`). Pre-existing, surfaced because the newly-exposed `palette_subject`/`sense` ride the same tool. — fix-shape: use the shared ISO8601 encoding — effort S.

### S10 [Low] Palette-group child-filter predicate duplicated ×3
The `.asset && .kind == .document` direct-children filter is independently written at `ProjectStore.paletteCardItems():63-65`, `PaletteLoading.paletteCards:14-17`, and `PaletteAimPicker.cardTitles:50-55` — none delegating to the shared `PaletteLookup` (which already centralizes the group lookup). In sync today; the sense-vocab case (S3) shows this exact copy-pattern already bites. — fix-shape: extract the child filter into `PaletteLookup` alongside the group lookup — effort S.

### S11 [Low] `promote_inbox_entry`'s "title ignored for palette promotes" is true but untested
The tool documents (`InboxTools.swift:125-127`) that `title` is honored for research promotes only; verified by inspection (`entry.title` never read by `promoteToPaletteCard`), but `InboxToolsTests` never passes `title` alongside `palette_card_id`/`palette_subject` to pin it — a future edit adding an image caption from `entry.title` would silently start honoring the ignored param. — fix-shape: one assertion (promote with both `title` and `palette_card_id`; assert card title unchanged) — effort S.

**Carry-forward (already on the 2026-07-11 shortlist, not re-counted):** MCP tool-count `47` is still hand-maintained prose (`CLAUDE.md`, `MCP/AREA.md`, `roadmap.md`) with no generation test — already §5 item 3 of the full audit; verified the count is currently exact (`MCPToolCatalog.all` = 47).
