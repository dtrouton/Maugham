## 2. Findings (each triaged in §3; every Medium coordinator-verified against source)

### P1 [Medium] `republish` overwrites the ORIGINAL edition's on-disk artifact → two catalog records point at one file, and the original publication silently serves drifted content
`Republisher.republish` re-renders from the frozen snapshot but the output *filename* comes from `PDFCompiler/EPUBCompiler.compile(label:)` against `snap.config`, whose `nextVersion` is pinned to the **original** `effectiveVersion` (`CompileOrchestrator.swift:220`, captured into the snapshot at `:295`). The distinguishing republish version `<v>-r<suffix>` is minted **after** the file move (`Republisher.swift:176-177`) and used only in the catalog record — never in the filename. `RepublishTool` passes `params.label` verbatim (`PublicationTools.swift:252`), so when the republish label matches the original (commonly both `nil`) the staged filename equals the original's; the move (`Republisher.swift:161-170`) does `if fileExists(dest) { removeItem }; moveItem` → **the original `Exports/` artifact is deleted and replaced**. Both the original `Publication` (version `vX`) and the new record (`vX-r<suffix>`) then resolve `outputPath` to the same file. Because `astSource` reads the **live** `ProjectStore` (Task 9 F1 comment `Republisher.swift:102-104` explicitly acknowledges the drift window), a manuscript edited since the original compile makes `read_publication_page`/`list_publications` for the original `vX` serve drifted bytes it was never published with. Repeated republishes all clobber the same path. — fix-shape: incorporate the `-r<suffix>` republish version (or the `publicationID`) into the republished output filename so it can never collide with the original artifact — effort M.

### M1 [Medium] Translation tombstone / orphan-deletion path is unreachable dead code → orphaned translations accumulate forever with no UI surface
`TranslationRecord` documents `text == nil` as a tombstone, and `TranslationStore.latestByParagraph`/`loadMerged` implement tombstone removal (`TranslationStore.swift:90-98`) — but **nothing can create one**. `write_translation` step 2 requires exactly one of `text`/`verbatim: true` (`hasText == isVerbatim` throws, `TranslationTools.swift:91-99`); when verbatim `text = source`, otherwise `text = e.text ?? ""` (`:120-124`), so the persisted `text` is never `nil`. Consequence: when a source paragraph is deleted, its translation is orphaned, only **counted** (`orphan_count` / `derived.orphans.count`, `TranslationTools.swift:244`) and **never surfaced or purgeable** — `TranslationReviewPane` shows source + queries only. This violates CLAUDE.md "every new data type needs a UI surface for inspection/action." — fix-shape: either delete the tombstone code as YAGNI, or add a delete/tombstone path (an MCP entry with explicit `delete: true`, plus an orphan-purge surface) — effort M.

### M2 [Medium] `translation_status` omits (doc, language) rows when a language has open translator queries but no translation files yet → the queries are invisible/uncounted
`translation_status` derives its language set purely from translation *filenames* (`TranslationStore.languages`, `TranslationTools.swift:312`), then buckets `open_queries` only within those languages (`:341`). A translator who raises `add_query(language: "fr")` **before** writing any `fr` translation produces no `fr` file → no `fr` row → the open query is invisible and uncounted, even for an explicit `document_id` (the explicit path resolves paragraph state but still iterates only the filename-derived `languages`). This is exactly the "ask a question first, translate after" workflow the `language` query-tag was added to support. — fix-shape: union the language set with the distinct `language` tags found on the doc's open `.query` annotations before building rows — effort S. *(Refuted collision: the `compile`/`republish` coverage GATE does not share this blind-spot — it runs `TranslationCoverage.check` against its explicit `language` param regardless of files; different code path.)*

### S1 [Low] W2-class joint-dedup gap survives in `renameResearchPath` (the #16 fix shared the ref-rewrite half but not the dedup half)
PR #16 unified the *ref-rewrite* helper (`rewriteAssetRefsBestEffort`) across `moveResearchItems` and `renameResearchPath`, but carried the W2 **joint note+assets dedup** across to `moveResearchItems` only. `renameResearchPath`'s asset branch dedups only the leaf via a `fileExists` while-loop (`ProjectStore+Research.swift:695`), then moves `<oldSlug>_assets → <dedupedSlug>_assets` (`:708`) with a destination that was never dedup-checked. If the parent dir already holds an orphaned `<dedupedSlug>_assets/` (from a manual `.md` delete or a prior partial failure), the `.md` move commits first (`:702`) and the assets move then throws on the existing destination → the note `.md` is at the new path but the function throws before the caller updates the manifest → **manifest↔disk divergence, identical class to the now-fixed W2**. Verified against source; NOT a regression of the W2 fix (whose scope was `moveResearchItems` only) — a pre-existing sibling the 2026-07-19 sweep already flagged as a duplication "watch." — fix-shape: route the rename through a joint note+assets dedup (reuse/generalize `researchDedupedNotePair`) so `<slug>_assets` is checked before the `.md` move commits — effort M.

### T1 [Low] `write_translation` is not atomic across its append loop despite the "nothing is written" contract
Pre-loop validation (unknown ids, intra-batch dupes, language tag) is truly all-or-nothing (`TranslationTools.swift:81-115`), but the per-entry `TranslationStore.append` loop (`:120-142`) can throw on entry N leaving 1..N-1 already persisted. Append-only newest-wins makes this self-healing on re-run, but the tool description's "an unknown id rejects the whole batch (nothing is written)" does not hold for a mid-batch I/O failure. — fix-shape: buffer the records and append once, or document the partial-write window — effort S.

### T2 [Low] The "translated text equals source → mark verbatim" advisory never fires for anchored paragraphs
`write_translation` compares Claude's (anchor-free) translation against the RAW `state.paragraphs[id]` still carrying `<!--t-XXXX-->` (`TranslationTools.swift:136`). For a paragraph with an inline task anchor, a genuine verbatim copy never equals the raw source, so the reminder — meant precisely for chrome/verbatim lines — silently never fires. Freshness hashing is unaffected (it `stripAnchors` on both sides). This is the concrete edge of a broader tension: **three** anchor-strip variants coexist in the translation path (`MarkdownDisplayFilter.stripAnchors` for the hash; `stripTaskAnchorsInline` for `read_translation` source; `RenderFilter.stripTaskAnchorsInline` for review badges). — fix-shape: compare against the same normalized/anchor-stripped source form used for hashing — effort S.

### T3 [Low] `TranslationStore` filename parsing is positional and assumes no `.` in docId/deviceSlug
`languages(forDocId:)` does `dropFirst(docId.count+1).dropLast(".jsonl".count).split(separator: ".")` expecting exactly 2 parts (`TranslationStore.swift:41-47`). Currently safe (language tags use hyphens per the regex, `DeviceSlug` alphabet is restricted, docIds are opaque), but it is unguarded positional string surgery; a docId that is a dotted prefix of another could theoretically cross-match. — fix-shape: parse the fixed-position tail segments from the right, or assert the component count — effort S.

### P2 [Low] Concurrent-compile race on the (version, language, format) collision guard
`CompileOrchestrator` loads `existingPublications` (`:123`), checks the triple (`:229-233`), and appends (`:362`) with no lock between load and append. Two concurrent identical `compile` calls both pass the guard and both append, producing two publications with the same triple (and, for source compiles, both grabbing the same `next_version`). The sibling TODO at `:355-361` acknowledges only the single-compile config-save/append gap, not this concurrent case. **Low likelihood** — a single MCP client issues serial calls — but deterministic and the fix is cheap. — fix-shape: serialize compile mints per project (actor/queue) or re-check the triple inside the append critical section — effort M.

### P3 [Low] Output filename not guaranteed to encode every identity-triple component → on-disk collision even when the catalog triple differs
`OutputFilenameBuilder` auto-suffixes only for the `{language}` case (`:56-63`); nothing requires the user's `filename_template` to contain `{version}`, and `PublishConfigValidator` does not validate it. A template lacking `{version}` maps two distinct source versions to the same file; both remain first-class catalog rows pointing at one path. The default template (`{title}-v{version}{label_suffix}.{ext}`) is safe. — fix-shape: validate `filename_template` contains `{version}` (and warn when a language project's template lacks `{language}`), or extend the collision guard to compare resolved output paths — effort S.

**Amendment (2026-08-09, issue #25 plan Task 3):** refuted — `PublishConfigValidator` has required `{version}` since its creation (`28b6fed9`, `PublishConfigValidator.swift:54-56`); this finding was wrong when filed. What was actually missing was the test pin, added in `MaughamTests/PublishConfigValidatorTests.swift` + `MaughamTests/RepublisherTests.swift`.

### P4 [Low] `ProjectStoreASTSource.allowStale` is a dead/misleading field
Documented (`ProjectStoreASTSource.swift:27-30`) as "stored so the gate can read the same value the substitution used," but the substitution (`translatedDisplayText`, `:102-104`) ignores it (always emits `translatedText ?? sourceText`), and neither gate caller reads it from the astSource: `compile` passes its own `allowStale` param to `applyGate` (`CompileOrchestrator.swift:268`) and `republish` uses `prior.allowStale` (`Republisher.swift:86,114`) while constructing the astSource with a hardcoded `allowStale: false` (`PublicationTools.swift:243`). Harmless today only because the substitution ignores it; a future reader trusting the doc-comment would be misled. — fix-shape: remove the field, or actually route it through substitution/gate — effort S.
