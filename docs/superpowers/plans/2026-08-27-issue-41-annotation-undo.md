## Findings, re-verified 2026-08-27 (both corrected)

- **A2 — real, and UI-reachable.** `Document.stetAnnotation` (`Maugham/OpLog/Document+Annotations.swift:805-844`) captures nothing before `appendLifecycleOp(.annotationStet)`; its undo (`:822-839`) ends in a bare `reopenAnnotation(id:)` (`:955-992`), which only ever produces `.open`. The op carries no prior status, so it cannot be recovered at undo time. Two of the three callers guard `.open` upstream (`AnnotationBulkActions.applies(.stet)` `:168-169`; the margin's `AnnotationFilter(statuses: [.open])`), but **`AnnotationsPane.swift:1302`'s row Stet does not**: `AnnotationRow.showsReopen` (`:1711-1716`) is `false` for `.accepted`, so with show-resolved on, an accepted comment/query/craft-note row offers Stet (`:1789-1811`); ⌘Z then flattens it to `.open`, losing the accept and its `Reply…` text. No MCP stet tool exists; merge never calls the verb. The issue's "correct only because UI stets open-only" is wrong — the pane does not.
- **A1 — real, symptom corrected.** Four per-item drift declines, not three: edit undo `:333`, **accept-note undo `:616` (on the bulk path, missed by the issue)**, stet undo `:834`, triage undo `:934`. `AnnotationBulkActions.perform` (`AnnotationBulkActions.swift:248-277`) registers one `OpUndoRegistrar` closure per note and `NSUndoManager.groupsByEvent` coalesces them (measured: `AnnotationBulkActionsTests.swift:311-345`). Drift is the annotation's own derived status changing since the action (a peer/phone acting, or the orphan sweep archiving a note whose paragraph was deleted) — NOT paragraph edits, so the issue's "edit 3 paragraphs" example yields 0 declines. And the toast is a single slot (`ProjectWindow.swift:3934/3964/3986` — `restoreToast = message`, same string → no re-render), so N identical posts show as ONE toast that says nothing about N, nor that the other notes DID undo. The defect is dishonesty, not spam.
