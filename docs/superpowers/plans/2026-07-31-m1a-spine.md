# M1A — The Spine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make intent and visual language one op-logged artifact — freeform prose with history, at project and per-document scope — and give visual language a reader in the same milestone.

**Architecture:** A `Statement` is registered in a new `ProjectManifest.statements` section and carried as an ordinary `Document`, so history, undo, merge and conflict handling arrive built rather than invented. It is edited in two right-hand panes that mount `EditorSurface` directly. Existing craft-intent research notes are adopted once, on open, through the op log's sanctioned bootstrap path.

**Tech Stack:** Swift 6, SwiftUI + AppKit, MaughamCore (local SPM, Apple frameworks only), TextKit 2, XCTest.

**Spec:** `docs/superpowers/specs/2026-07-31-m1a-spine-design.md`. The spec is authoritative; where this plan and the spec disagree, the spec wins and the plan is wrong.

---

## How this plan is written, and why it looks different

**This plan carries contracts, symptoms and verified signatures — never function bodies.** That is a project rule (CLAUDE.md, `memory/feedback_plan_code_is_a_liability.md`) and it overrides the generic plan-writing convention of pasting implementation and test code inline. The reason is measured: on M1C, plan-supplied function bodies became the shipped defect, and four separate implementers had to correct plan text written against an API that did not exist yet.

So each task gives you:

- the **files**, with `file:line` for every existing thing you must touch;
- the **contract** — what must be true when you are done;
- the **test's subject and its falsification** — what the test asserts, and what change to production code must make it fail. Name the test what the task names it; the name is how the next task's reviewer finds it.
- the **signatures you will consume**, quoted only where they were read out of the tree on 2026-07-31 and cited.

**You write the test body and the implementation.** If a contract here is wrong, or a signature has drifted, **say so and stop** — refusing a stated ruling you can falsify is the standard here, not insubordination. Two implementers did exactly this on the previous slice and both were right.

**Tasks 7–10 are deliberately requirements-only.** Task 6 re-derives them against the code tasks 1–5 actually built. Do not implement 7–10 from their current text.

## Global Constraints

Copied from CLAUDE.md and the spec. Every task's requirements implicitly include this section.

- **The op log is the source of truth.** `.md` on disk is derived and anchor-free (ADR 0019). External `.md` edits are discarded, never ingested.
- **`Bootstrap.run` must be called from any new manuscript load path.** The contract surface is `Document.load`; route new load paths through it and construct `Document` no other way. `BootstrapWiringTests` enforces this.
- **Plain text on disk.** Manuscript-and-statement content lives in the open at the writer's paths; only derived state goes under `.maugham/`.
- **MCP never mutates manuscript text.** This slice adds no write tool of any kind.
- **Move/delete of user-editable content goes through the typed `DocumentStore` mover** — `relocate` / `relocateUserContent` / `trash` (tripwire 14, grep-enforced by `TripwireGrepTests.test_noRawMoveOfUserContentOutsideTypedMover`).
- **Anything touched by both Mac and phone goes through a shared `MaughamCore` implementation** (tripwire 19). The phone must not reimplement what the Mac implements.
- **No parallel observable state on `EditorHost`; no 4th caller of `EditorSurface.applyExternalText`** (tripwires 6, 7).
- **No bare `ParagraphID.mint()` in production** — use `mintUnique(excluding:)` (tripwire 23).
- **4-char alphabet-restricted paragraph ids in tests crossing the `.md` ↔ op log boundary** — `[0-9a-hjkmnp-tv-z]` (tripwire 8).
- **No prose counts of list members.** Name the members, or point at the array. A number in prose about a list is a defect when written (`memory/feedback_prose_counts_are_unmaintainable.md`).
- **`Maugham.xcodeproj/` is generated.** Run `./gen.sh` after adding any file; never hand-edit `project.pbxproj`; never commit anything under `Maugham.xcodeproj/`.
- **macOS 14 floor, iOS 17 floor.** Both stay for this milestone.

## Task 1: The `Statement` type and the manifest section

**Files:**
- Create: `Packages/MaughamCore/Sources/MaughamCore/Statement.swift`
- Modify: `Packages/MaughamCore/Sources/MaughamCore/ProjectManifest.swift:29` (`currentSchemaVersion`), `:72-82` (stored properties), `:122-135` (memberwise init)
- Test: `Packages/MaughamCore/Tests/MaughamCoreTests/StatementTests.swift`

**Interfaces:**
- Consumes: nothing.
- Produces: `Statement` with `id: String`, `kind: Statement.Kind`, `scope: Statement.Scope`, `path: String`. `Kind` is `.intent | .visualLanguage | .unknown(String)`. `Scope` is `.project | .document(String) | .unknown(String)`. `ProjectManifest.statements: [Statement]`. Every later task depends on these exact names.

**Contract:**

1. `ProjectManifest.currentSchemaVersion == 4`.
2. `statements` is a non-optional `[Statement]` on the manifest, defaulting to `[]` in the memberwise init so no existing construction site breaks. It must **decode as empty when the key is absent** — a schema-3 manifest has no such key and must still open.
3. `Kind` and `Scope` are **lossless** on unknown values, following `ResearchRole` (`ResearchItem.swift:18-51`) and *not* the lossy `ItemType`/`AssetKind` shape. Read that type's doc comment before writing yours; it explains why identity-bearing enums preserve the raw string and benign ones don't. A statement is the writer's prose — there is something to preserve on behalf of a newer build.
4. `Scope` carries an associated value, so like `ResearchRole` it cannot be a `String`-raw enum and the `Codable` conformance is hand-written. On-disk shape for a document scope is your choice; state it in the type's doc comment and pin it with a round-trip test.

**Why the bump is not ceremony** (put this in the doc comment, because the next person will ask): `statements` decodes as absent-tolerant, so an older build would read the project happily and then re-save the manifest **without the section**, destroying the registry that points at the writer's intent files. `decodeGuardingSchema` (`ProjectManifest.swift:112`) is what prevents that.

**Contract:**

`resolveDocId(for:)` currently matches the URL's project-relative path against `manifest.structure` via `findItemByPath`, and falls through to `"doc-\(StableHash.fnv1a64Hex(relativePath))"` when nothing matches (`:314-329`). ## Task 3: Find-or-create a statement by scope

**Files:**
- Create: `Maugham/Stores/ProjectStore+Statements.swift`, `Packages/MaughamCore/Sources/MaughamCore/StatementLookup.swift`

**Interfaces:**
- Consumes: `Statement`, `ProjectManifest.statements` (Task 1).
- Produces:
  - `StatementLookup.statement(in:kind:scope:) -> Statement?` — pure, no stamping, no side effects. Mac and phone both call it (tripwire 19).
  - `ProjectStore.statement(kind:scope:) -> Statement?` — the Mac's reading wrapper.
  - `ProjectStore.createStatement(kind:scope:) async throws -> Statement` — idempotent find-or-create.
  - Tasks 5, 7, 8 and 9 all call these by these names.

**Contract:**

1. **Lookup is by `scope`, in the manifest.** There is no path prefix and no filename convention in the read path. This is what kills the defect rather than fixing it — see the spec's §3 and the comment block at `PromotionPerformer.swift:498-512`, which documents the defect from the inside.
2. `createStatement` is **idempotent**: called twice for the same `(kind, scope)` it returns the same statement and creates no second file.
3. Paths are minted per the spec's §2.2 table — `intent.md`, `intent/<slug>.md`, `visual-language.md` — with `<slug>` derived from the document's title **at creation and never re-derived**. Identity is the manifest `id`; the path is free to drift after a rename.

5. A scope that names a document id not in `manifest.structure` **throws** rather than silently falling back to project scope. The old seam documented this discipline (`ProjectStore+CraftIntent.swift:28-31`) and it is worth keeping.

`StatementLookup` mirrors `PaletteLookup` (`PaletteConvention.swift:15-46`): pure lookups, no stamping, so the Mac can wrap them with whatever healing it needs and the phone can use them read-only.

## Task 4: Adopt existing craft-intent notes, once

**Files:**
- Create: `Maugham/Stores/StatementAdoption.swift`
- Modify: `Maugham/Stores/ProjectStore.swift:221-275` (the load path)
- Test: `MaughamTests/StatementAdoptionTests.swift`

**Interfaces:**
- Consumes: `ProjectStore.createStatement(kind:scope:)` (Task 3); `Document.load` (unchanged); `DocumentStore.relocateUserContent(affectedPaths:perform:)` — verified at `DocumentStore.swift:586`.
- Produces: the adoption entry point, called from `ProjectStore.load`.

**Contract:**

1. **The gate is the on-disk schema version.** Adoption runs when the manifest reads `schemaVersion < 4`; the post-adoption save writes 4. Gating on "has no `statements` section" instead would re-scan forever a writer who legitimately has no intent.
2. **The content arrives as a bootstrap op**, through the path `Document.load` already takes for an imported plain file with an empty op log — the `needsBootstrap` branch, which `Document+Load.swift:104-110` calls the sanctioned import read. Adopted intent therefore has history starting at adoption, not no history.
3. **Duplicates concatenate, oldest first**, separated by a blank line. The defect in the spec's §3 has been minting second copies; picking a winner discards the writer's prose. Concatenating is recoverable, choosing is not.
4. **Detection is role-first with the filename as fallback** — `ResearchRole.craftIntent`, then `PaletteConvention.craftIntentFileName` — mirroring `PaletteLookup.craftIntentItem`'s two tiers (`PaletteConvention.swift:23-32`), so a note the writer renamed is still found.
5. **The note's file moves through the typed mover.** `DocumentStore.relocateUserContent(affectedPaths:perform:)` closes, flushes and unregisters before your `perform` runs. A raw `moveItem` here is tripwire 14 and is grep-enforced: the 750ms autosave will recreate the file at the old path afterwards, leaving a phantom.
6. **Failure must not block the open.** A project that cannot be adopted still opens, with the legacy note untouched and an error logged. Losing access to your manuscript because an intent note was odd is a worse outcome than un-adopted intent.

**The precedent to follow, and it is exact:** `ProjectStore.load` already performs a one-time, on-open backfill — the project-id backfill at `:263-275`. Read its comment, including why it deliberately leaves `modified` untouched (*"backfilling an identifier is not a content edit"*). Adoption is a content move, so decide and state whether `modified` should shift; do not leave it accidental.
