Within each group, items are listed roughly small-first. Each group's "next up" is the suggested first concrete milestone, but groups are independent — pick what to work on based on day-to-day friction, not a linear order.

**Comprehensive ⌘Z undo (op-log-backed):**
- • **Unified ⌘Z undo across every op kind** — today ⌘Z only undoes in-editor text edits (AppKit's native undo on the `NSTextView`); op-log mutations made *outside* the keystroke stream are NOT undoable with ⌘Z. Concretely, **accepting or rejecting a suggestion can't be undone** (noticed 2026-06-28) — neither can a task toggle/reorder, an annotation accept/withdraw, a checkbox flip, etc. The History Rewind modal (2026-05-21) can restore a doc to an earlier op, but that's a deliberate forensic tool, not the muscle-memory ⌘Z a writer reaches for. Since the op log already records every mutation with its `prior`/`next` (and lifecycle ops carry `sourceAnnotationId`), we have everything needed to make ⌘Z a first-class, op-log-backed undo/redo stack that spans text edits AND annotation/task/checkbox lifecycle ops — by appending a compensating op (e.g. accept → a new op that reverts the paragraph + reopens the annotation) rather than mutating history (stays append-only). Design questions to brainstorm before scoping: how the unified undo stack interleaves AppKit's native text-undo with op-log undo (one stack or two?); per-document vs project scope; how it reconciles with History Rewind (shared cursor?); redo semantics; and how cross-device merges (ADR 0012) interact with a local undo stack. Likely reuses the `RewindCursor` / `SynthesisSource` machinery.

A transferable **author lock** governs who may edit the manuscript; everyone else — human collaborators *and* Claude — operates in the existing annotation layer (comments, queries, suggested changes, surfaced in `AnnotationsPane` with Accept/Reject/Archive). **Design direction (provisional, 2026-06-06):**
  - **Three roles.** *Project owner* — persistent, singular (whoever created the project). *Author* — the current per-document lock-holder; the only one who may edit that doc. *Reviewer* — everyone else (human collaborators and Claude), annotation layer only.
  - **Lock = a transferable baton.** One holder per document; only the holder can edit. Only the holder can **release** (or flip themselves to review mode); once released, another collaborator may **claim** it. The **project owner** — and only the owner — can **force-takeover** a held lock (warned override), so an unreachable lock-holder can't freeze the project.
  - **Per-document granularity** (rides the per-doc op-log / per-device-JSONL grain), with **project-level "Claim all / Release all"** so the solo-writer case is one action and the co-authored collection case (Alice owns story 1, Bob owns story 2) works in parallel.
  - **Attribution:** reuse the existing annotation `OpKind`s; add an `author`/`source` provenance field so a named human reviewer is distinguished from Claude in the pane. Identity is a per-device display name set in Settings — no accounts.
  - **Access models, both in scope:** (1) shared iCloud-Drive folder, each collaborator on their own Mac, comments sync via per-device JSONL ([ADR 0012](adr/0012-per-device-jsonl-partitioning.md)); (2) a local **reviewer-mode toggle** on the writer's own Mac (the degenerate single-device case of the same lock).
  - **Deferred questions:** how owner identity is established and stamped on a shared folder (candidate: at project creation, alongside the minted `ProjectManifest.id`); where the lock lives for collection *project-references* vs loose docs; whether Claude's annotations should be visually grouped separately from human ones. Brainstorm to full spec before scoping.
  - **VCS-steals to fold in when scoping** (surfaced in the 2026-06-07 backup brainstorm): **patch commutation / real merge** (Darcs/Pijul) to replace crude LWW-by-paragraph for multi-author concurrent edits; **signed generations/checkpoints** (git/hg signed tags) so a collaborator's contribution carries verifiable provenance (ties to the **Backup & integrity** signing primitive); **blame / annotate** per-paragraph who/when-last-changed (the op log already holds per-op device/session/at).
  - **Skew-aware LWW + same-paragraph conflict surfacing is owned here** (deferred out of the 2026-06-07 hardening milestone, which shipped only merge/derive *determinism* — see `Maugham/OpLog/AREA.md`). Starting point: the audit's 0.2 (skew-induced cross-device LWW loss) + the `prior`-snapshot divergence-detection idea in `docs/superpowers/notes/2026-06-07-codebase-audit.md`; the authored-but-skipped `CrossDeviceIntegrationTests` case 4 records the scenario.
  - **Supersedes** the deferred "Shared folder collaboration" surface — the author lock *is* the locking/conflict-avoidance model that surface said it needed.

**MCP correctness:**
- ✓ **`read_document` / `add_comment` paragraph-sequence skew** (flagged 2026-06-28, via Claude Desktop; fixed by ADR 0018, shipped v0.12.4) — `add_comment` rejected a paragraph id (`paragraph_not_found`) that `read_document` had just returned, because `read_document` read a stale `.md` verbatim for closed docs while `add_comment` derived fresh from the op log. `read_document`'s closed-doc path now derives from the op log too (`DerivedManuscript`), so both walk one `sequence` and agree by construction. This was the motivating bug for ADR 0018.

- ✓ **`list_all_links` / `find_references` open-doc freshness** (ADR 0018 follow-up, shipped 2026-07-01 in the op-log-spine-hardening branch) — both now take the live `Document`'s in-memory state when the doc is open (the `store.documentStore?.document(for:)` branch `read_document` / `list_scenes` use), so a `[[wiki]]` typed-but-not-yet-flushed in an OPEN editor is no longer missed. The earlier "~750ms" framing understated the lag it closed: an open doc's ops land at the **burst window's close (30s idle / 90s cap / force-flush)**, not at the 750ms autosave — the autosave writes the `.md` + pending mirror but appends no ops. Consistency, not correctness.

See [ADR 0021](adr/0021-scoped-window-events.md).
- ✓ **Zombie-window teardown mitigation (workaround 1, 2026-07-02)** — the spike's retain-root trace pinned SwiftUI's `static GraphHost.sharedGraph` as the retainer of a closed `WindowGroup` scene's view graph (so `dismantleNSView` never runs on ⌘W), and showed the payload is almost entirely OUR `@State`. Since the ROOT scene view's `.onDisappear` (`ProjectWindow`) fires on close, we empty the zombie ourselves — measured & iterated in three parts: (1) `ProjectWindow.onDisappear` scorches its heavy `@State` (`store`/`documentStore`/`lastParsedScript`) under an `isLive` guard and `MaughamTextView.viewWillMove(toWindow: nil)` detaches the coordinator on the close path `dismantleNSView` misses (→ 0 live coordinators); (2) `DocumentStore.close()` drains its document registry (a nested `@State`'s stored `DocumentStore` kept it alive — a NESTED view's `.onDisappear`, e.g. EditorHost's, does NOT fire on window close, so its unregister was unreliable); (3) `Document.close()` husks its own O(doc) in-memory state (paragraphs/op-log-mirror/caches) because EditorHost's `@State` box for the `Document` stays retained by the dead scene and can't be nil'd from outside. EditorHost.onDisappear remains a belt for the segment-switch abandonment case only. Expected residual drops from tens of MB per closed window to SwiftUI's AttributeGraph husk (100s of KB). **Future escalation** (its own milestone, NOT this workaround): explicit `NSWindowController` hosting to actually release the scene — trigger to schedule it is a manual footprint A/B still showing material residual after this mitigation, or long-session RAM creep from repeated open/close of large projects.
