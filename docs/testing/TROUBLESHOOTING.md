## A test fails in the parallel suite but passes alone

**The Mac scheme runs test classes in parallel worker processes** (`parallelizable: true` in `project.yml`, 2026-08-08): full suite went 7.6 → 2.75 min on the first parallel run, then to **~70-90s** once the canvas-mounting class split let its 68s spread across workers; 4,624 tests, no skips. Each worker hosts its own app process, so window-mount tests don't collide. A test that fails in the parallel suite but passes alone now has THREE possible confounders — apply the in-suite/in-isolation discriminator before blaming your branch; check whether it assumes a globally unique resource (fixed socket path, shared UserDefaults key, a hardcoded temp dir) that another worker can hold at the same time; and check for OTHER SESSIONS' builds with **`pgrep -x xcodebuild`, never `pgrep -f xcodebuild`** — `-f` matches the whole command line, and this harness puts a shell wrapper carrying the word `xcodebuild` in the process table, so an agent guarding on `-f` matches ITSELF and every other waiter (three agents deadlocked ten minutes on an idle machine, 2026-09-19, one of them holding `test.sh`'s global lock while parked). For the same reason **no wait loop may carry `xcodebuild` in its own command line**: put a loop that must invoke it in a script FILE and run the file, so the waiter's argv doesn't read as a running build to everyone else. With several Claude sessions on one Mac, two overlapping full gates host 14+ app processes, and starvation-shaped failures land on a different victim each run. `test.sh` gates queue behind a machine-global lock (2026-08-08), so this confounder survives only for RAW `xcodebuild` invocations, which bypass it — one more reason to prefer `test.sh` (measured 2026-08-08: two overlapped gates, two runs, two different single failures — an ordering-poll deadline and a zero-baseline perf control reading 15 — both green in isolation, one in a file untouched for weeks).

## A 0.000s crash with "attempt to insert nil object" in a styling test

**A 0.000s crash in a typography/styling test with `attempt to insert nil object from objects[0]` is the fontd cold-start window, not your change.** AppKit's nonnull-annotated font APIs (`NSFont.monospacedSystemFont` et al.) can return nil while the machine-global `fontd` daemon is being hammered — seven fresh worker processes resolving their first font at gate start. Confirmed from a captured xcresult 2026-08-08 (two sightings in ~16 gates, both 0.000s, both styling suites). `FontWarmup.ensure()` in `override class func setUp()` absorbs it — wire it into any NEW suite that styles text through production typography paths; `test.sh full` keeps an xcresult per run precisely so a one-off like this arrives with its crash text.

## A red PDF-compile test whose response carries "errors": []

**A red PDF-compile test whose response carries `"errors": []` is the tectonic bundle fetch, not your LaTeX.** `TectonicLogParser` only recognises lines beginning `! `, so an empty errors array with a non-zero exit means typesetting never began — the bundled `tectonic` died fetching its TeX Live bundle from a third-party host. Cost run 31874029028 eight red assertions in `PublishingEndToEndTests` that said nothing about the code (2026-08-15; the same gate re-fetched successfully 8.3s later in another suite, and a plain re-run was green). Two fixes shipped: CI caches the bundle (keyed on `scripts/fetch-tectonic.sh`, restore/save **split** so a red gate still seeds it), and **every suite that shells out to tectonic calls `try await TectonicProbe.requireReady()`** instead of hand-rolling an is-it-bundled guard. Wire it into any NEW suite that performs a real compile. Its canary is deliberately a bare `\documentclass{article}` using nothing this app emits, so an emitter/template regression still goes red rather than skipping — **do not give the canary a dependency**; `TectonicProbeTests` pins it. Note `log_excerpt` is `prefix(4000)` — the HEAD of a cold log is pure `note: downloading …`, so where it appears to stop is the truncation point, not the failure. See `docs/superpowers/notes/2026-08-15-tectonic-bundle-fetch.md`.

## A Core test dies with only "Test Case … started."

**A red Core `swift test --parallel` whose only output is one test's `Test Case '…' started.` — no assertion, no crash report, a different trivial test each time, green on a re-run — is an `xcodebuild test` starting somewhere on this Mac, not your branch.** Every `xcodebuild test` (either scheme, any session) SIGKILLs every process NAMED `xctest` as it begins testing, and SwiftPM's parallel runner hosts each Core test in one (proven 2026-09-25 with a decoy: `/bin/sleep` copied as `xctest` died with 137 two seconds before an unrelated run's "Testing started"; the same binary under its own name lived). Run Core through `./scripts/test.sh core`, which takes the gate lock, rather than a bare `swift test`; a raw `xcodebuild` from another session still bypasses it.

## "The test runner hung before establishing connection" on several workers

**"The test runner hung before establishing connection" / "Timed out while preparing execution worker", on 3–6 of 7 workers, with ZERO assertion failures, is a bloated `$TMPDIR` — not memory, not contention, and not your branch.** Proven by `sample` on three live stuck workers, 2026-09-11: all three were 100% in one frame — `MaughamApp.init()` → `TestHost.applyActivationPolicyIfHosting` → `StaleFileSweep.sweep` → `contentsOfDirectory` — enumerating a temp directory holding **543,002 entries** on the main thread, BEFORE XCTest can connect, which is exactly why nothing names a test or an assertion. The entries are **our own leaked test fixtures** (`CompilerRunComman…`, `AnnChar…`, `DiagnosticsStor…`, `MaughamTests…`, `DesignerOrchestrator…`, `MRB-*` at 2.2 MB each, and a dozen more prefixes): every gate makes the next gate slower, which is why the signature arrived gradually and why the surviving-worker count varies run to run. Two earlier diagnoses were tested and are WRONG — it is not memory (3 workers hung at 74% free) and it is not seven concurrent Secure Enclave mints (zero enclave frames in any sample). **The code fix landed in P2b's final wave (2026-09-11), in two halves.** The sweep is bounded — `StaleFileSweep.sweep` enumerates lazily (`FileManager.enumerator`, never `contentsOfDirectory`, which materialises the whole listing before the first name is examined) and stops at `defaultEntryBudget` (2,000 entries) or `defaultTimeBudget` (0.25 s), sweeping only what it saw; and `TestHost` dispatches it to a background queue, so a reaper of yesterday's orphans has no claim on the launch path whatever it costs. The leak half is fixed in the seven suites the samples named (`MCPResponseBudgetTests`, `CompilerRunCommandTests`, `AnnotationsCharacterization`, `DiagnosticsStoreTests`, `DesignerOrchestratorTests`, `TranslatorOrchestratorTests`, `TranslatorEnvironmentTests` — each now tracks its fixture roots and removes them in `tearDown`); **The leak half is closed tree-wide by P3 plan 3's Task 1 (2026-09-26)** — see the `TestTemp` bullet below; a backlog from before it is still worth clearing once on a machine that has been running gates for days. Do not re-derive the falsified hypotheses.

## A test leaves fixtures in the temp directory, or a socket bind skips silently

**Every test builds under `TestTemp`, and nothing else in a test target names the machine's temp directory (2026-09-26, P3 plan 3 Task 1).** `TestTemp.root` is `$TMPDIR/MaughamTests-worker-<pid>/<uuid>/`, one per test, and an `XCTestObservation` removes it at `testCaseDidFinish` whatever the test did or forgot to do. `TestTemp.workerRoot` (`…/shared/`) is for a fixture built in `class func setUp()`; it lives until `testBundleDidFinish`, which removes the whole worker folder. A root asked for before its test has started (a class setUp, or a stored property's initialiser) belongs to the class, not the first test. A dead worker's folder is swept by `DeviceState`'s pid rule, at most once every ten minutes across processes (a stamp in `$TMPDIR`), off the main thread. The file exists as byte-identical copies in `MaughamTests/TestSupport/`, `MaughamPhoneTests/` and `Packages/MaughamCore/Tests/MaughamCoreTests/`, guarded by `TripwireGrepTests.test_theThreeTestTempFilesAreIdentical`. The census is `TripwireGrepTests.test_noTestNamesTheTempDirectoryButTestTemp` plus its phone twin: it bans `temporaryDirectory` and `NSTemporaryDirectory(` outside `TestTemp.swift`, and its allow-list is FILE plus SPELLING, an array with a reason each, for tests asserting on a PRODUCTION temp path (`TestHostSocketPathTests`) — count the array, not this bullet. **A Unix socket cannot be bound under `TestTemp.root` by absolute path**: the root alone is about 112 bytes and `sun_path` holds 104, so bind by name from inside the directory as `StaleFileSweepTests` does (the old absolute spelling skipped silently on every run). The test host's launch sweep also removes dead workers' `xctest-worker-<pid>` leaves under `TestWorkspace` and `device`, and `TestWorkspace.reset()` removes the leaf without re-making it.

## A mounted click test sees selectedRow == -1

**A mounted synthetic-click test needs the test host to be the ACTIVE app — and activation is OPT-IN, because it takes the writer's keyboard.** With `loginwindow` frontmost (screen locked) or another app refusing to yield activation, AppKit drops the synthetic `mouseDown` before any view sees it: `selectedRow` stays −1 at a poll deadline, indistinguishable from a code bug until you check `ioreg -n Root -d1 | grep ScreenIsLocked` and `NSApp.isActive`. Measured 2026-08-13 across three modes (locked, user-active, idle-unlocked — only the last clicks). Since the headless gate (2026-08-27) the host never activates itself unless `MAUGHAM_ALLOW_ACTIVATION=1` is in its environment — `TestWindow.activate(_:)` is the one sanctioned way to ask, and CI sets `TEST_RUNNER_MAUGHAM_ALLOW_ACTIVATION=1` (the runner has no writer to interrupt). **Measured the same day, and not what the 2026-08-13 note predicts: on an `.accessory` host the click lands WITHOUT activation** — `NSApp.isActive` false, another app frontmost, `NSApp.keyWindow` nil, all five `TreeTravelRowMountingTests` clicks green in a plain local gate — so a local run gets these tests for free and takes nobody's keyboard. The 2026-08-13 measurements were made on a `.regular` host; which of the two changes (policy, or the hidden window) buys it is not isolated. The skip is still there for the case that does fail (a locked screen) and is decided on a measurement, never on `NSApp.isActive` alone (`TreeTravelTests.click(at:)` is canonical; it also quiesces the event queue first — stale `appKitDefined` traffic from ordering a window front otherwise feeds NSTableView's drag-disambiguation loop and eats the pair). Before trusting an overnight or during-use gate, read its skip list; before blaming a red click test, check the lock state.

## A test window, sheet, beep or Dock tile appears during a gate

**The gate is headless (2026-08-27): every test window is built by `TestWindow` and every worker is an `.accessory` app.** Sixty test files used to build their own visible titled window at the screen's origin and order it front — across seven parallel workers that was hundreds of windows and seven bouncing Dock tiles for the length of every gate, and it made the Mac unusable while one ran. Now `MaughamTests/TestSupport/TestWindow.swift` is the one place a window is constructed (`TestWindow.make`/`.mount`, `present: .front/.key/.unshown`, your subclass passed as `type`): the window is **real and hidden** — on screen for the window server (`occlusionState` `.visible`, so SwiftUI lays out, `onAppear` fires, `TimelineView` ticks, key status is grantable), drawn at alpha 0, deaf to the real mouse, out of Mission Control and the Window menu. `TestHost` in the app switches an XCTest host to `.accessory` at launch (no Dock tile, no ⌘-tab) **and sweeps every window the host shows into the same concealment** — a sheet is its own child window at full alpha whatever its parent's, and the first hidden gate floated `DesignGateTests`' "Finalize this design" dialog over the desktop as an orphan popup; alert panels, popovers and the Welcome scene would do the same. The fixture's default class is `SilentTestWindow`, because the beep AppKit makes for every keystroke no responder claims was the other thing the flashing windows had been hiding. **Two things were measured, not assumed**: the full gate is green under this configuration with a skip list identical to the visible one, and moving windows OFF screen does not work — AppKit clamps a titled window's origin back onto the screen, so "off-screen" silently meant "visible". `TripwireGrepTests.test_noWindowIsPresentedOutsideTheTestWindowFixture` fails on `backing:`/`orderFront(`/`makeKeyAndOrderFront(` anywhere else under `MaughamTests/`, so a new suite cannot bring the flashing back; the shared `KeyTestWindow` (reports key without an active app; `reportsKey` is flippable) replaced six private copies. Anything that must construct a window by hand gets an allow-list entry there, not an exemption comment.

## A unit test stalls ~64 s on an NSOpenPanel

**A unit test that allocates a real `NSOpenPanel`/`NSSavePanel` can stall ~64s on the window server's XPC service under parallel-worker contention** — not lock-state-dependent (green gates were observed with the screen locked, so a lock-state skip was rejected as the fix). `BinderTreeDropRoutingTests.test_theTreesAddFilePanelTakesFoldersAsWellAsFiles` hit this six times across three milestones (2026-08-16..19) before the fix: it used to call `BinderTreeVerbs.makeAddFilePanel()`, which built a live panel. Fixed by extracting the configuration into a pure value (`AddFilePanelConfiguration` in `Maugham/Views/BinderTreeSections.swift`, applied via `.apply(to:)` to a panel only production ever constructs) and asserting the value in the test — nothing in the suite touches AppKit's panel machinery any more. If a NEW test needs to pin an `NSOpenPanel`/`NSSavePanel` configuration, follow the same shape: a plain struct the test can construct and compare, never a panel the test allocates.

## The dev app's compiler checks say "couldn't be read as notes" after a gate

**A gate no longer unlinks an open dev app's MCP socket (2026-09-06) — but a build from before that fix does; relaunch the app after one.** Every launch of the app starts an `MCPServer` from the Welcome scene's `.task`, and seven parallel XCTest workers are seven launches. `MCPServer.start()`/`stop()` and `MaughamApp`'s `willTerminate` observer each `unlink` the path, so `./scripts/test.sh` used to **delete the socket file the developer's open dev app was listening on**, with nothing red anywhere: the app keeps its listening descriptor, while every `claude -p` spawned afterwards reports `mcp_servers: [{maugham-dev, failed}]` and the writer sees a compiler check that "couldn't be read as notes". `TestHost.mcpSocketPath` is now the one decision — the variant's path for a writer, `<temp>/maugham-host-<pid>.sock` for a host — and `TripwireGrepTests` keeps `BuildVariant.current.mcpSocketPath` out of `MaughamApp.swift`. Diagnosed from Denver's smoke of the two-loops milestone; the symptom is the socket directory's mtime matching the gate.

## MaughamCore's tests did not run

**MaughamCore's package tests belong to NO scheme.** Until 2026-08-08 they ran nowhere — not locally, not in CI (the "Mac app + MaughamCore" comment this section used to carry was false). CI's `core-tests` job and both `test.sh` modes now run them; run `./scripts/test.sh core` after touching `Packages/MaughamCore` (a bare `swift test` bypasses the gate lock — see the xctest-kill bullet below).

## A MaughamCore change is green in one scheme only, or the simulator says "Busy"

**The two schemes are independent.** A change to MaughamCore should be tested against BOTH (plus the package's own `swift test`). Transient simulator "Busy / failed preflight checks" is a flake — re-run; don't `simctl shutdown all` before a launch.

## The suite is slow while iterating

**Iterating? Skip the mounted-canvas suites until the end.** The `CanvasViewMounting*` family mounts a real window per test and costs ~70s across the three of them — about a sixth of the suite's total EXECUTION time (the wall cost is smaller now that the three classes spread across workers) — while every other canvas suite together finishes in ~37s. It is **three classes over one shared base**, `CanvasViewMountingCase` (harness only, no tests): `CanvasViewMountingSurfaceTests` (the mount, the cards, the accessibility tree), `CanvasViewMountingEditingTests` (typing, undo, save, Escape, ⌫, selection) and `CanvasViewMountingRegionTests` (sweeps, regions, membership, lines) — split 2026-08-08 so Xcode's per-class parallel scheduling can put them on three workers instead of pinning the suite's wall time to one. **`-skip-testing:` and `-only-testing:` take the CONCRETE class names; naming the base does nothing.** When the change doesn't touch the canvas view/event/undo/save wiring, add all three skips during iteration — or just run `./scripts/test.sh`, which carries them. It is NOT optional before calling work done: run the full suite before merge/tag. The suite already runs on shortened real clocks (`makeModel()`, 2026-08-08) — the remaining cost is the per-test window mount, so don't try to claw it back with shorter pumps.

## The full gate fails on the skip count

**`./scripts/test.sh full` fails when more Mac tests skip than `scripts/skip-baseline.txt` names**, and lists the skips it does not hold. A new skip is usually an environment gone missing (tectonic, the mcp binary, an AX client, a second volume): restore it and re-run. If the skip is deliberate, add its `Class/test()` line and give the reason in the commit message. Fewer skips pass with a hint to delete the stale lines. The check is local-only: `CI` set turns it off.

## A mounted-view test is red on CI only

**CI's macOS must not drift from the dev machine's, or mounted-view tests become untrustworthy in one direction only.** The Mac jobs run the **`xcode-27` runner + Xcode `27.0`** because that is what the developer machine runs; the deployment target is **macOS 27** for the same reason (2026-09-19, shell slice D2/D4 — before that it was `macos-26` + 26.6 + a target of 26, on the identical rule). From 2026-08-02 to 2026-08-04 CI sat on `macos-15` — two majors behind — and a test that mounts a real `NSSegmentedControl` measured 24pt locally and 224pt there, because SwiftUI's segmented `Picker` FILLS its container below macOS 26 and HUGS its content at 26. Two `SceneNavigatorProjectRowTests` cases that synthesise clicks hung for the full 2-minute allowance on the old runner and finished in under a second locally. Both suites were green on the developer machine the whole time and red on every CI run since the day they landed. **A green local suite says nothing about a mounted-view test if the two OSes differ** — check the runner image before believing "works here, broken in CI" is a flake. Only `phone-tests` and `phone-release.yml` stay on `macos-15`; they build the iOS app, whose floor is iOS 17. **And matching the OS is not matching the DISPLAY**: the runner's virtual screen is 1024pt wide against this Mac's 1470, `NSWindow` silently clamps to it, so a mounted test that asks for a wide window gets a narrow one and any assertion about what that width affords fails on CI alone — three `DetailColumnWidthTests` cases did exactly that on run 31339238337 (macos-26, Xcode 26.6 — the pin at the time). A mounted test must read its premise off the window it actually got, and skip by name where the display cannot afford what it is about. **The 2026-09-15 drift is CLOSED (shell slice, 2026-09-19): both sides are on 27 and the gap is gone.** The dev machine moved to Xcode 27.0 / macOS 27 on 2026-09-15 and CI sat on `macos-26` for four days, during which fifteen mounted-view tests were red locally and green in CI — the interim, not a standing state. `xcode-27` is the label (there is no `macos-27`, and `macos-latest` is still 26); it is a public-preview image, accepted under D2, and it now carries Xcode **27.0 RELEASE (27A266a)**, the dev machine's exact build, rather than the beta 6 the drift note recorded. **A red mounted test is now yours, with no interim list to check it against.** Two residues of the move outlive it: the SDK declares `SwiftUI.Document`, which `MaughamTests/TestSupport/DocumentDisambiguation.swift` shadows — do not qualify `Document` in test files; and `NavigationSplitView`'s undocumented column tie-break flipped at 27, so the detail column's width is defended by the pane's own framing rather than by that tie-break. See `docs/superpowers/notes/2026-09-18-macos-27-sdk-drift.md` and its Outcome.

## A build fails in Release only

**After any `ProjectWindow.body` change, run a local Release build before tagging** (`xcodebuild … -configuration Release build CODE_SIGNING_ALLOWED=NO`). The Release type-check budget is stricter than Debug.

## Phantom "Undefined symbol" after a signature change

**Clean DerivedData after merging public-init / protocol-signature changes** to avoid phantom `Undefined symbol` link errors against stale `.o` files.

## A warning census reads clean on an incremental build

**A warning census over `xcodebuild` output is only as good as whether the file was COMPILED in that invocation.** An incremental build re-emits nothing for a file it did not touch, so grepping a warm build for warnings reads exactly like a clean file. `touch` the file (or clean) before believing the absence. Cost the 2026-08-04 escape-monitor work one wrong "resolved" from the implementer AND one from the reviewer, on the same warning, in the same hour.

## SourceKit diagnostics

**Triage SourceKit diagnostics by class.** Most are noise (`No such module`, stale index). Trust `xcodebuild`. **Exception: `the compiler is unable to type-check this expression in reasonable time` is REAL** — heed it. Blanket-ignoring is how a Release-only build failure shipped to CI on v0.8.0. **Second exception: a `Sendable`/concurrency diagnostic on a file you just wrote is real** — SourceKit reported one on a new canvas file (2026-08-04) that two separate `xcodebuild` greps declared absent.

## A project.pbxproj shows up in a diff

**`Maugham.xcodeproj/` is generated, not tracked.** `project.yml` is the source of truth; `./gen.sh` produces the whole `.xcodeproj/`. Never hand-edit `project.pbxproj`; never commit anything under `Maugham.xcodeproj/`.

**Watch for stray `project.pbxproj` edits in diffs.** `Maugham.xcodeproj/` is generated and gitignored; a pbxproj in a diff is a red flag.

## MCP tests hang or park (history)

**ROOT-CAUSED 2026-08-15 — every xctest host runs AT libdispatch's 64-thread ceiling, and that is what parked `MCPServerLifecycleTests`.** `sample` on a live stalled gate says it outright: *"Dispatch Thread Soft Limit: 64 reached in 3490 of 3490 samples — too many dispatch threads blocked in synchronous operations"*, with 63 of 69 threads in `-[NSAnimation _runBlocking]`. **The same app launched normally has 10 threads and one of them** — this is a test-host condition, not a product defect, and it is present before the first test runs (measured against a pure, non-mounting suite). At the ceiling a `DispatchQueue.global(...).async` block is at the governor's mercy: usually scheduled in microseconds, else delayed indefinitely from the test's point of view — a **19-minute release was actually observed** (M3-P2 sighting, gate passed at 1130s), so wall clock alone never distinguishes a park from a crawl, and the 120s per-test allowance is what makes it decidable — hence the effectively bimodal **0.006s-or-forever** signature. The 10s `SO_RCVTIMEO` added by `5fe107b` could not save it because the timeout lives INSIDE the block that never ran. Fixed by reading on a dedicated `Thread` (not pool-drawn), so the deadline can always fire; `test.sh` now also passes CI's `-test-timeouts-enabled YES -default-test-execution-time-allowance 120`, whose absence locally is why all three sightings were local. **`MCPServer.blockingAccept`/`blockingRecv` moved to dedicated `Thread`s in the same pass** — a blocking syscall on a dispatch worker holds it, and as written MCP would silently stop answering if anything saturated GCD (latent in production, live in the host); with that, **two consecutive full local gates are green, 5,780 passed / 0 failed**, where the four before it failed 1–3 of this family each. **And the animations are macOS WINDOW RESTORATION** — `lldb` attached at exec caught `_NSWindowTransformAnimation` under `-[NSApplication _reopenWindowsAsNecessaryIncludingRestorableState:]` → SwiftUI's `AppWindowsController.showInitialWindows()` → `makeKeyAndOrderFront:`, one blocking-on-a-dispatch-worker animation per restored window, none of which ever completes in a host whose windows are never really presented. **`project.yml`'s test action now passes `-ApplePersistenceIgnoreState YES`**, which is why the ceiling is gone (`DiagnosticsPaneTests`: 74 threads / 51-63 blocked / limit reached → 37 / 6 / not reached, same 75 passing). Wanted independently of the hang: the host was reopening whatever project windows the DEVELOPER had open, a hidden dependency on machine state. This is also why suppressing the Welcome scene changed nothing — the restored windows are not that scene. Do not re-derive the two falsified hypotheses (a per-test window leak in `DiagnosticsPaneTests`; the Welcome window's appearance animation) — both were tested and are recorded as wrong turns.
